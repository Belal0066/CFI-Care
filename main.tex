\section{Methodology}

The implementation of the AI system is structured in three iterative phases, each focusing on core capabilities and scalability.

\subsection{Phase 1: Prototyping and Core AI Modules}

\subsubsection*{Tools and Frameworks}
\begin{itemize}
    \item \textbf{Language Models}: GEMMA-Med, BioGPT, Mistral, or open LLaMA variants (3B–8B)
    \item \textbf{RAG Systems}: LlamaIndex, LangChain, Haystack with vector DBs (FAISS, ChromaDB)
    \item \textbf{Evaluation}: MLflow Evaluation, BERTScore, BLEURT, human-in-the-loop
\end{itemize}

\subsubsection*{Components}
\begin{itemize}
    \item \textbf{Medical Question Answering} \\
    - Using Fine-tuned LLMs with domain-specific embeddings (e.g., PubMedBERT).
    - Retrieval pipelines using patient data and context-aware augmentation.

    \item \textbf{Symptom Checker / Triage} \\
    Rule-based hybrid with language models trained on guideline-driven datasets.

    \item \textbf{Graph RAG for Long-Term Records} \\
    Use patient history as a versioned graph (GitMed). \\
    $\rightarrow$ Traverse timelines with semantic search and dynamic context windows.
\end{itemize}

\subsection{Phase 2: Integration and Optimization}

\subsubsection*{Goals}
\begin{itemize}
    \item Deploy lightweight LLMs with retrieval (RAG) to minimize compute costs.
    \item Run AI workloads in scalable, secure containers (e.g., FastAPI + Uvicorn + Ray Serve).
\end{itemize}

\subsubsection*{Components}
\begin{itemize}
    \item \textbf{Event Detection (Streaming AI)} \\
    Use threshold-based ML on IoT data streams for real-time alerts (SpO\textsubscript{2}, ECG, etc.)

    \item \textbf{Multimodal Input Support} \\
    OCR/ASR preprocessing pipelines (e.g., MarkItDown) for ingesting raw clinical notes, images, and audio into AI-friendly structured formats.

    \item \textbf{Knowledge Graph Integration} \\
    Structure medical history as a graph, annotated with AI metadata, linking symptoms $\rightarrow$ tests $\rightarrow$ diagnoses $\rightarrow$ treatments.
\end{itemize}

\subsection{Phase 3: Full-Scale Intelligent Platform}

This platform will deliver secure, scalable, and efficient health monitoring with AI-assisted analysis, accessible via both web and mobile. The chosen stack enables rapid development, strong security, and consistent functionality across platforms through a shared backend.

\section{Architecture Overview}
Both the \textbf{web} and \textbf{mobile} apps will connect to a \textbf{shared Express.js backend} via secure REST + WebSocket APIs. This backend centralizes business logic, data processing, and AI integration, ensuring consistent results.  

\noindent\textbf{Data Flow:}  
\[
\text{Frontend (Web/Mobile)} \rightarrow \text{API Gateway} \rightarrow \text{Backend (Express.js — flexible for NestJS)} \rightarrow \text{Database (PostgreSQL + Redis)}
\]

Mobile requests are optimized for smaller payloads, while the web app can fetch more detailed datasets.

\section{Justification}
This stack ensures:
\begin{itemize}
    \item \textbf{Security} – Encryption, RBAC, and compliance-ready architecture protect patient data.
    \item \textbf{Scalability} – Modular backend leaves open the option to move from Express.js to NestJS if project complexity grows.
    \item \textbf{Performance} – Optimized payloads ensure fast load times for mobile and detailed analytics for web.
    \item \textbf{Cross-platform parity} – Shared backend guarantees identical AI results and business rules across devices.
    \item \textbf{Developer efficiency} – Popular frameworks (Angular, Flutter, Express.js) enable rapid feature delivery and long-term maintainability.
\end{itemize}

\section{Health Connect}
\subsection{What is Health Connect?}
\begin{itemize}
        \item A built-in Android 14 app (APK) that stores and manages health & fitness data on the device.
        \item Apps can read, write, and share data after receiving explicit user permission.
        \item Health Connect is packaged with Android 14 as part of the Android system, which means you cannot uninstall it from a device.
\end{itemize}

\subsection*{Why Use Health Connect?}
\begin{itemize}
    \item Unified access to multiple types of health data.
    \item Data remains on the device, ensuring privacy.
    \item Permissions Management: Request only the data types required (e.g., READ_HEART_RATE, READ_STEPS).
    \item Interoperability across multiple apps and devices.
\end{itemize}

\subsection{Core Components}
\begin{enumerate}[leftmargin=*]
    \item \textbf{Health Connect APK} -- Pre-installed on Android 14 devices; manages permissions \& data storage.
    \item \textbf{Health Connect SDK} -- A library integrated into the app to communicate with the APK via IPC.
    \item \textbf{Client Application} -- The developer’s application that uses the SDK to access approved data types.
\end{enumerate}

\subsection{Supported Data Categories}
\begin{itemize}[leftmargin=*]
    \item \textbf{Activity}: running, swimming, cycling, steps.
    \item \textbf{Body Measurement}: weight, BMI, BMR.
    \item \textbf{Cycle Tracking}: menstrual cycles, ovulation test results.
    \item \textbf{Nutrition}: calories, sugar, hydration.
    \item \textbf{Sleep}: sessions, duration.
    \item \textbf{Vitals}: heart rate, blood pressure, oxygen saturation, body temperature.
    \item For more info \href{https://developer.android.com/health-and-fitness/guides/health-connect/plan/data-types}{Health Connect Data Types}
\end{itemize}
\section{Evaluation}
\subsection{Challenges and Solutions}
\begin{itemize}
\item \textbf{Device Fragmentation}: Numerous devices and OS variants can complicate consistent testing. Cloud platforms offer access to real devices and parallel testing to address this.

\item \textbf{Frequent Updates}: Regular OS and app updates require continuous maintenance. AI-powered self-healing tools can automatically adjust tests.

\item \textbf{Network Variability}: Testing under different network conditions is essential; simulation tools help mimic real-world networks.

\item \textbf{Maintaining Test Scripts}: Breaking tests into modular components improves maintainability.

\item \textbf{CI/CD Integration}: Integration challenges can be overcome by automating test executions within CI tools like Jenkins or GitHub Actions.

\item \textbf{Limited Access to Real Devices}: Cloud device farms provide extensive real device access without physical inventory.

\item \textbf{Setup Complexity}: Cloud testing services simplify environment setup and configuration.

\item \textbf{Cross-Device Functionality}: Tools like Appium support uniform testing of gestures and interactions across platforms.
\end{itemize}
\subsection{Mobile test automation tools and frameworks}
\begin{itemize}
\item \textbf{Selenium and Appium}:are great for cross-platform testing. Selenium supports multiple browsers (Chrome, Firefox) and operating systems (Windows, macOS). It works well for web apps and allows parallel testing with Selenium Grid. Appium is perfect for mobile app testing and supports both Android and iOS.
\item \textbf{For API testing}: Postman is a great option. It's free and allows you to send requests, automate tests, and inspect responses.
\item \textbf{JMeter}: is another option for performance and load testing, simulating multiple users and measuring app performance under stress.
\item \textbf{Playwright}: automates browser interactions and simulates real user behavior. It supports cross-browser testing (Chrome, Firefox, Safari) and provides control over browser contexts, network conditions, and user actions. It’s perfect for end-to-end testing of web apps.
\end{itemize}

\section{Methodology}
\textbf{Milestone 1: OCR \& NLP Implementation-Testing}

\subsection{Optical Character Recognition (OCR)}
We will integrate an OCR pipeline to digitize lab reports in image or PDF format, ensuring compatibility with scanned documents and handwritten notes where applicable.

\textbf{Planned Implementation:}
\begin{itemize}
\item Use the \textbf{Google Cloud Vision OCR API} for high-accuracy text extraction, leveraging Google’s powerful pre-trained models optimized for printed and handwritten text.
\item Enable multi-language recognition (Arabic and English) using Google OCR’s language hints feature for bilingual reports.
\item Perform client-side pre-processing for image enhancement (e.g., noise reduction, skew correction) before sending to the API to improve OCR accuracy.
\item Integrate Google OCR API calls within a secure backend environment, ensuring all data is encrypted in transit and at rest according to HIPAA compliance.
\item Store original scanned lab report images and extracted text securely in the database for reference and audit purposes.
\end{itemize}


\subsection{Testing Plan and Estimated Timeline}

\textbf{OCR Testing:}
\begin{itemize}
\item \textbf{Accuracy Testing:} Evaluate recognition accuracy by comparing Google OCR API output with ground truth text from diverse printed and handwritten lab reports.
\item \textbf{Language Support Testing:} Verify correct extraction of bilingual content using Google OCR’s language hinting and multi-language support.
\item \textbf{Pre-processing Effectiveness:} Assess the impact of client-side image enhancements on OCR accuracy and output quality.
\item \textbf{Security Testing:} Confirm that data transfer to Google Cloud is encrypted and that processed data complies with HIPAA standards, ensuring no PHI leakage.
\end{itemize}

\subsection{Natural Language Processing (NLP) Summarization}

Once OCR extracts the textual content, an NLP module will summarize the results for quick review by medical staff.

\textbf{Planned Implementation:}
\begin{itemize}
    \item Use medical-domain NLP models (e.g., \textbf{BioBERT}, \textbf{MedGPT}) fine-tuned for laboratory and pathology data.
    \item Apply Named Entity Recognition (NER) to detect and highlight important terms such as biomarkers, diagnosis results, and measurement values.
    \item Generate concise summaries while preserving critical clinical details.
    \item Provide a structured output compatible with the FHIR Observation resource format for interoperability.
    \item Store generated summaries alongside the original OCR text in the database for future retrieval, search, and analysis.
\end{itemize}
