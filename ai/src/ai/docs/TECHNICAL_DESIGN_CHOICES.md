# Technical System Design & Tradeoffs
## Clinical RAG System for Longitudinal Patient Reasoning

This document outlines the core architectural choices and the associated tradeoffs made during the development of the Clinical RAG system.

---

### 1. Model Selection: MedGemma 1.5 (4B/9B)
- **Choice:** MedGemma 1.5-4B-IT (Quantized to Q6_K).
- **Justification (Why MedGemma?):** 
    - **Clinical Domain Pre-training:** Unlike general-purpose models (e.g., Llama-3), MedGemma is fine-tuned on the **CMM (Clinical Multi-Modal)** and medical literature datasets. This provides it with a native understanding of medical terminology (ICD-10, SNOMED-CT) and clinical reasoning patterns (SBAR, SOAP).
    - **Local Sovereignty:** Open-weights allow for internal hosting, ensuring patient data (PHI) never leaves the institution's secure perimeter, addressing HIPAA/GDPR concerns at the source.
    - **Efficiency/TPS Optimization:** The 4B variant occupies ~5.4GB VRAM in Q6_K, allowing for high tokens-per-second (TPS) even on consumer-grade GPUs (RTX 2070/3060), which is critical for real-time physician interaction.
- **Tradeoff:**
    - **Capability vs. Latency:** While 70B+ models offer better multi-step reasoning, the 4B/9B variants provide significantly lower latency at a fraction of the hardware cost.

### 2. Inference Engine: llama.cpp
- **Choice:** `llama-server` (C++ backend).
- **Justification (Why llama.cpp?):** 
    - **Low-Level Control:** Provides direct access to KV-cache management and rope-scaling, essential for handling the long, dense clinical timelines generated by our compiler.
    - **Hardware Optimization:** Native support for CUDA and AVX-512 ensures high inference speed on a wide range of hospital edge-compute hardware.
- **Tradeoff:**
    - **Feature Set:** Lacks some advanced features found in vLLM (like continuous batching) but offers superior memory efficiency for single-user clinical environments.

### 3. Embeddings: ModernPubMedBERT
- **Choice:** `lokeshch19/ModernPubMedBERT`.
- **Justification (Why ModernPubMedBERT?):** 
    - **Medical Vocabulary Mastery:** Standard encoders often get "confused" by clinical abbreviations (e.g., "SOB" for shortness of breath or "ESRD" for end-stage renal disease). PubMedBERT treats these as single semantic units.
    - **Dimensionality (768-D):** Provides a robust representation while maintaining efficient HNSW indexing overhead.
- **Tradeoff:**
    - **Context Window:** Restricted to 512 tokens, requiring our custom **Atomic Ingestion** strategy to prevent semantic fragmentation.

### 4. Vector Database: Qdrant
- **Choice:** Qdrant (Dockerized).
- **Justification (Why Qdrant?):** 
    - **Advanced Payload Filtering:** In a clinical environment, multi-tenancy is critical. Qdrant allows for **Hard Scoped Filtering** (e.g., `WHERE patient_id = 'XYZ'`) *during* graph traversal, ensuring a physician never accidentally retrieves data from the wrong patient manifold.
    - **Quantization Support:** Native **Scalar Quantization (int8)** reduces memory footprint by 4x while maintaining >99% retrieval accuracy, allowing the entire patient index to reside in RAM.
- **Tradeoff:**
    - **Complexity:** Requires Docker overhead but provides superior stability for safety-critical services.

### 5. Orchestration: LangGraph
- **Choice:** LangGraph (StateGraph).
- **Justification (Why LangGraph?):** 
    - **Cyclic Reasoning:** Clinical diagnosis is rarely linear. It requires cycles (e.g., "Summarize -> Detect Missing Lab -> Search External Guideline -> Refine Summary"). LangGraph allows for **Actual Graph Cycles**, which are impossible in standard "Linear Chains."
    - **Persistence & Checkpointing:** LangGraph manages session state natively. If an inference fails or a physician pauses, the exact state of the clinical reasoning graph is persisted.
    - **Deterministic Control:** Offers "State Machines" rather than open-ended agents, providing the predictability required in medicine.

### 6. External Interop: FastMCP (Model Context Protocol)
- **Choice:** FastMCP / Model Context Protocol.
- **Justification (Why FastMCP?):** 
    - **Schema-Driven Interop:** Instead of brittle custom REST adapters, MCP provides a standard protocol by Anthropic for model-to-tool communication. This ensures the model receives **Cleaned Clinical Nuggets** instead of raw noisy HTML/JSON.
    - **Decoupled Architecture:** By running the MCP server as a separate microservice (Port 8002), we isolate the heavy scraping/external API logic from the core Patient RAG pipeline, preventing blocking UI threads.

### 7. Hybrid Reasoning Pipeline: Deterministic + Stochastic
- **Choice:** Unified Hybrid Reasoning (Tickets 4-10 integration).
- **Why:** 
    - **Hallucination Mitigation:** Relying purely on an LLM to parse raw FHIR often leads to "hallucinated" dates or findings. Our system uses a **Deterministic Patient State Compiler** to first build a ground-truth timeline, which is then handed to the LLM for high-level reasoning.
    - **Auditability:** Every claim made by the LLM can be traced back to a specific node in the deterministic state.
- **Tradeoff:**
    - **Development Effort:** Building a custom state compiler is more labor-intensive than simply "dumping everything into a prompt," but it is the only way to ensure clinical safety.

### 6. RAG Configuration & Context Construction
- **Embedding Segmenting:** Query embeddings use `lokeshch19/ModernPubMedBERT` with a 768-dimension vector space. The model uses **Mean Pooling** and a maximum sequence length of **512 tokens**.
- **Top-K Strategy:** Defaulting to `k=5` for retrieval to balance context density with the model's effective attention window.
- **Context Formatting:** Context is presented to the LLM as a chronological "Clinical Timeline" with explicit Node IDs (e.g., `[node-123]`) and semantic tags (e.g., `[Observation]`, `[Medication]`) to enable the **Reasoning Layer** to cite sources.
- **Separation of Thought:** The system uses specific synthesis markers (`CLINICAL SYNTHESIS:`) in the system prompt. This forces the model to perform internal chain-of-thought (CoT) reasoning before providing final clinical conclusions.

### 8. MedMCP: Real-Time Authority
- **Architecture:** FastMCP based microservice running on port 8002, utilizing the **Model Context Protocol (MCP)** for seamless integration with AI agents and IDEs.
- **Routing Engine:** Employs **LangGraph** to manage the stateful flow of external retrieval:
    1. **Guardrail Node:** Filters out pseudoscience or harmful queries (Class G).
    2. **Classification Node:** Uses Llama 3.3 70B to extract entities and optimize keywords.
    3. **Search Node:** Dispatches concurrent requests to **OpenFDA** (for Class C), **PubMed** (for Class D), and **MedlinePlus** (for Class B).
    4. **Summarizer Node:** Synthesizes raw search results into concise, clinically relevant context.
- **Latency Optimization:** Uses Groq's LPU for classification and summarization to keep total external retrieval time under 10 seconds.

### 9. Clinical Agent Reasoning (Tickets 9-10)
- **Bounded Reasoning:** The agent is strictly constrained to only use the provided context. If data is missing (e.g., "Patient's HbA1c is not available"), it must state the missing data rather than inferring a value.
- **Temporal Tracking:** Automated identification of longitudinal trends (e.g., "Glucose has increased from 110 to 180 over 3 months"), which is handled by comparing `dateIssued` ISO-8601 metadata.
- **Deductive Flow:** The agent follows a multi-step internal reasoning process:
    1. **Data Review:** Summarize all relevant findings from retrieved nodes.
    2. **Temporal Synthesis:** Analyze changes over time.
    3. **Differential Contextualization:** Integrate external MCP evidence with patient-specific data.
    4. **Final Synthesis:** Provide cited clinical conclusions.
- **Citation Enforcement:** Every claim in the `ClinicalResponse` object is mapped to a `CitedClaim` model, ensuring 1:1 parity between statement and evidence.

### 10. Data Ingestion: Patient State Compiler
- **Choice:** Deterministic normalization of FHIR-derived JSON into a "Normalized Timeline".
- **Why:** 
    - **LLM Context Density:** Raw FHIR JSON is verbose and token-heavy. Normalizing into a narrative-style timeline maximizes the information density within the LLM's limited context window.
    - **Consistency:** Ensures the LLM always sees data in a predictable, chronological format.
- **Tradeoff:**
    - **Schema Rigidity:** The ingestion pipeline is coupled to a specific input contract. Changes to the source FHIR mapping require updates to the preprocessor.

### 11. Frontend: Streamlit
- **Choice:** Streamlit-based Interactive Dashboard.
- **Why:** 
    - **Developer Velocity:** Allows for rapid iteration of the UI based on physician feedback without a dedicated frontend team.
- **Tradeoff:**
    - **Customization:** Limited control over low-level UI/UX compared to React/Next.js, but sufficient for internal clinical tools.

### 12. Networking & Security: Tailscale Funnel
- **Choice:** Tailscale for secure remote access.
- **Why:** 
    - **Zero-Trust:** Provides end-to-end encryption and identity-based access without requiring complex VPN or reverse proxy configurations.
    - **Compliance:** Minimizes technical surface area for potential attacks on PHI-carrying services.
- **Tradeoff:**
    - **Dependency:** Reliance on a third-party service for mesh networking, though extremely reliable.

### 13. Testing, Benchmarks, and Clinical Evaluation
The system underwent a rigorous three-tiered evaluation process to ensure clinical safety and performance.

#### **A. Clinical Faithfulness (Groundedness)**
- **Objective:** Quantify the hallucination rate and ensure every claim is backed by source data.
- **Results:** 
    - **Faithfulness Score:** 1.0 (100% of claims supported).
    - **Hallucination Rate:** 0.0%.
- **Methodology:** A text-overlap heuristic verifies that symbols and clinical facts in the generated answer exist in the retrieved nodes.

#### **B. Retrieval Recall (Search Effectiveness)**
- **Objective:** Evaluate how well `ModernPubMedBERT` identifies relevant clinical events.
- **Results:**
    - **Recall@10:** 87.5% (High probability that relevant data is in the context).
    - **Mean Reciprocal Rank (MRR):** 0.675.
- **Conclusion:** Dense vector retrieval is highly effective at scoping relevant longitudinal events, especially for summarization and trend identification tasks.

#### **C. Pipeline Latency (Overhead Analysis)**
- **Objective:** Measure the computational overhead of the deterministic reasoning layers.
- **Results:**
    - **Mean Pipeline Latency:** ~0.15ms (excluding LLM inference).
    - **Primary Driver:** Query Intent Classification (~0.06ms).
- **Impact:** The deterministic logic adds negligible overhead compared to LLM generation (typically 2-10s), ensuring that safety checks do not impact the user experience.

### 13. Agentic Architecture & Functional Roles
The system employs a multi-agent orchestrated architecture where specialized roles are assigned to different computational nodes (both deterministic and stochastic).

#### **Structural Roles**
| Role | Component | Responsibility |
|------|-----------|----------------|
| **Router** | `IntentClassifier` | Analyzes incoming queries to route between local RAG, external MedMCP, or safety guardrails. Checks for PII/PHI leakage and blocks non-clinical spam. |
| **Planner** | `QueryRewriter` | Decomposes complex clinical questions (e.g., "Why did my patient's heart rate spike last week?") into multi-step search sub-tasks and keyword optimizations. |
| **Executor** | `ContextRetriever` / `MedMCP` | Performs the physical work of data extraction. Fetches vectors from Qdrant or scrapes medical literature from PubMed/OpenFDA. |
| **Critic / Auditor**| `ClinicalReasoner` | Post-processes generated answers. Verifies that every claim has a valid `node_id` citation and rejects any synthesis that introduces "hallucinated" clinical facts. |

### 14. Agent Interaction & State Management
The "Agentic" behavior is defined by how these components communicate and maintain state throughout a clinical session.

#### **A. Tool-Calling vs. Reasoning-Only Paradigms**
- **Reasoning-Only (MedGemma):** To protect PHI, the internal MedGemma model operates in a "sandboxed" reasoning mode. It cannot directly call internet-facing tools; it only reasons over the context *prepared* for it by the executors.
- **Tool-Calling (MedMCP):** The MedMCP acts as a high-privilege tool proxy. It uses the **Model Context Protocol (MCP)** to execute internet searches and API calls, returning structured summaries that the reasoning model can safely ingest.

#### **B. Memory Management**
- **Transient Memory (Context Window):** Managed via a priority-based context construction script that ranks retrieved snippets by "clinical relevance" and "recency" to fit within the model's 16k context window.
- **Long-Term State:** Handled by the **Patient State Compiler**. Instead of relying on the LLM to remember past encounters, the compiler persists a deterministic representation of the patient's entire longitudinal history in a structured cache.

#### **C. Agent Communication Patterns**
- **Orchestrated Linear Pipeline:** The primary workflow for clinical summaries follows a strict DAG (Directed Acyclic Graph): `Preprocessing` → `State Compilation` → `Retrieval` → `Synthesis`.
- **Hierarchical Delegation:** For external evidence queries, the system uses a delegation pattern. The primary coordinator (Streamlit Backend) pauses the local reasoning flow to "hand off" keywords to MedMCP, waiting for the structured evidence return before proceeding.
- **Event-Driven Feedback:** The system supports a "Verification Loop" where if the Auditor (Critic) detects a claim without a citation, the Planner is re-triggered to expand the search radius in Qdrant to find the missing evidence.

### 16. Core RAG Infrastructure & Retrieval Paradigms
The Retrieval-Augmented Generation (RAG) pipeline is the technical foundation of the system, transforming unstructured clinical data into actionable context.

#### **A. Indexing Strategies: Atomic Event-Based Indexing**
Unlike general-purpose RAG systems that use **Fixed-Size Sliding Window Chunking** (e.g., 500-character chunks with 50-character overlap), our system utilizes **Atomic Clinical Event Indexing**.

*   **1:1 Node Mapping:** Each document in the vector store corresponds strictly to one `NormalizedNode` (a single FHIR resource like an Encounter or Observation).
*   **Context Preservation:** By treating clinical events as atomic units, we avoid the "Partial Context" problem where a lab result is split across two chunks, causing the LLM to lose the association between a value and its metadata.
*   **Semantic Boundary Alignment:** The "Chunk" is defined by the clinical event itself. If an event is smaller than the model's 512-token limit, it is indexed as a single entity.
*   **Overflow Handling:** For rare, extremely large clinical notes (e.g., a lengthy discharge summary), the system applies a **Top-Down Truncation** strategy, prioritizing the definitive assessment and treatment plan, which usually reside at the end or beginning of the note.

**Why No Fixed-Size Chunking?**
Standard sliding-window chunking is rejected because medical records are inherently **non-linear**. Splitting a "Diagnosis" resource at Character 500 might leave the diagnosis name in Chunk A and the justifying clinical evidence in Chunk B, leading to fragmented retrieval where the LLM sees the conclusion but not the proof. Atomic indexing ensures that the reasoning signal remains unified.

#### **B. Embedding Model: ModernPubMedBERT**
- **Model Architecture:** A BERT-based encoder fine-tuned on the **ModernPubMed** dataset, specifically optimized for clinical terminology and abbreviations.
- **Pooling Strategy:** Uses **Mean Pooling** over the last hidden layers to generate a robust 768-dimensional representative vector.
- **Normalization:** Vectors are L2-normalized to allow for **Cosine Similarity** search, which is resilient to variations in document length.

#### **C. Vector Database & Search Backend: Qdrant**
- **Indexing Algorithm:** Uses **HNSW (Hierarchical Navigable Small World)** graphs. This provides $O(\log N)$ search complexity, enabling sub-millisecond retrieval across millions of clinical records.
- **Quantization:** Employs **Scalar Quantization (int8)** to reduce memory footprint by 4x while maintaining >99% retrieval accuracy.
- **Isolation Groups:** Utilizes Qdrant's payload indexes to enforce strict **Tenant Isolation** by `patient_id`, ensuring no cross-contamination of clinical context.

#### **D. Retrieval Paradigms**
- **Dense Vector Retrieval:** The primary mechanism for capturing semantic similarity (e.g., mapping "high sugar" to "elevated blood glucose").
- **Multi-Hop Retrieval:** For complex causal queries (e.g., "What caused the tachycardia?"), the system performs an initial anchor search for the symptom and then a secondary hop to retrieve temporally preceding medications or lab results.
- **Hybrid Context Construction:** The results are not just a list of snippets, but a **Relational Context Block** where nodes are ordered chronologically to preserve the patient's narrative flow.

#### **E. Query Reformulation & Decomposition**
- **Step 1: Intent Expansion:** The `QueryRewriter` expands natural language abbreviations (e.g., "HTN" -> "Hypertension") before embedding.
- **Step 2: Sub-Query Decomposition:** Questions involving multiple clinical domains are split. "Analyze my patient's respiratory status and current antibiotics" is decomposed into:
    1. Retrieval for `[Observation: Respiratory]`
    2. Retrieval for `[Medication: Antibiotics]`
- **Step 3: Multi-Stage Filtering:** The system applies dynamic filters based on the detected intent (e.g., a "Treatment" query automatically boosts the weights of `Prescription` and `Procedure` nodes in the retrieval results).

### 17. System Architecture & End-to-End Flow
The following section describes the operational flow and data connections as outlined in the system architecture diagram.

#### **A. Data Ingestion Pipeline (The Knowledge Base)**
This is a deterministic, unidirectional flow that populates the vector store:
1.  **FHIR Data Ingestion:** Raw JSON resources are ingested into the `ToonNormalizer`.
2.  **Semantic Normalization:** The `ToonNormalizer` strips FHIR-specific verbosity and converts resources into a human-readable text format ("Toon") while preserving semantic tags.
3.  **Patient State Compilation:** The `Patient State Compiler` groups events chronologically, building a longitudinal "state" of the patient.
4.  **Vectorization:** Each compiled node is embedded via `ModernPubMedBERT` and stored in the **Qdrant Vector DB** with persistent UUIDs for traceability.

#### **B. Query Inference Pipeline (The Reasoning Loop)**
The workflow for a clinician's query follows a state-managed orchestration:
1.  **Entry Point:** The Clinician interacts with the **Streamlit Dashboard**, which communicates with the **FastAPI Backend**.
2.  **Orchestration:** The **LangGraph Agent** takes control of the request, maintaining the session state.
3.  **Triage:** The **Intent Classifier** analyzes the query, and the **Routing Logic** branches based on the need:
    *   **Path 1: Patient-Specific Query:** The `RetrievalStrategy` executes a scoped search in **Qdrant**. The hits are passed to **Context Assembly**, which formats the raw vectors back into a structured clinical timeline.
    *   **Path 2: General Medical Query:** The system invokes the **MCP Client**, which performs external retrieval from **PubMed/Internet** sources.
4.  **Synthesis:** Assembled context (either internal patient data, external medical evidence, or both) is fed into the **MedGemma 1.5** model (hosted via `llama.cpp`).
5.  **Generation & Citation:** The model generates a response using its internal chain-of-thought. The **Generation & Citation** layer then performs a final alignment check to ensure all clinical claims are grounded in the provided context before returning the answer to the Clinician.

#### **C. Key Connections & Protocols**
-   **Qdrant to Retrieval:** Uses gRPC/REST for high-speed vector retrieval.
-   **LangGraph to MCP:** Uses the **Model Context Protocol** (SSE transport) for decoupled tool execution.
-   **Reasoning Layer to MedGemma:** Uses an OpenAI-compatible API layer provided by `llama-server`.
-   **Grounding Plane:** A feedback loop exists between the `Generation & Citation` node and the `Context Assembly` to verify that every ID cited by the LLM is physically present in the retrieved set.

### 18. Architectural Subsystems (Deep Dive)
This section provides a rigorous technical breakdown of the three primary pillars of the system: the **Agentic Core**, the **RAG Infrastructure**, and the **Model Context Protocol (MCP)** service.

#### **A. Agentic Core (LangGraph Orchestration)**
The agent is implemented as a **StateGraph** in `langgraph`, managing a directed acyclic graph (DAG) of functional nodes.

**1. Architecture & State Management**
*   **State Schema (`ClinicalAgentState`):** A typed dictionary that persists context across the graph execution lifecycle.
    *   `patient_state`: Immutable, deterministic snapshot of the EHR data.
    *   `retrieved_docs`: Serialized list of clinical documents from Qdrant.
    *   `internet_evidence`: External data fetched via MCP tools.
    *   `mode`: Control flag (`auto`, `local`, `mcp`, `chat`) determining the routing logic.
*   **Graph Topology (Execution Nodes):**
    *   **`classify` [Entry]:** The triage node. It executes the `IntentClassifier` to determine if the query is local (Patient Specific) or external (Medical Knowledge).
    *   **Conditional Router (`route_intent`):** Logic that branches based on the `mode` flag (`auto`, `local`, `mcp`, `chat`) or the detected intent.
    *   **`rag_retrieve`:** Executes the `MedGemmaRAG` engine to fetch vectors from Qdrant based on the clinical intent (e.g., boosting medication nodes for therapy queries).
    *   **`reason`:** The **Deterministic Logic** node. It takes raw retrieved nodes and uses the `PatientStateCompiler` to build a "Ground Truth" temporal sequence before the LLM ever sees it.
    *   **`mcp_search`:** The external handoff. It invokes the **FastMCP** service to fetch PubMed guidelines or OpenFDA drug interactions.
    *   **`generate`:** The stochastic synthesis node. It feeds the assembled context (Local or External) into **MedGemma** to produce the final cited response.
    *   **`END`:** Terminal node that returns the final `ClinicalResponse` object to the UI.

*   **State Machine Transitions:**
    1.  `START` $\rightarrow$ `classify`
    2.  `classify` $\xrightarrow{\text{intent}}$ `rag_retrieve` (if patient-related)
    3.  `classify` $\xrightarrow{\text{intent}}$ `mcp_search` (if medical-knowledge-related)
    4.  `classify` $\xrightarrow{\text{mode=chat}}$ `generate` (direct zero-context chat)
    5.  `rag_retrieve` $\rightarrow$ `reason` $\rightarrow$ `generate`
    6.  `mcp_search` $\rightarrow$ `generate`
    7.  `generate` $\rightarrow$ `END`

**3. MCP "Auto-Transition" Logic**
When the system is in `mode: auto`, the LangGraph router implements a three-tier fallback mechanism to trigger an MCP search:
1.  **Semantic Triggers:** The `IntentClassifier` detects keywords related to external authority (e.g., "guidelines," "FDA," "recent research"). This sets the `is_mcp_query` flag to `True`.
2.  **Zero-Data Isolation:** If the `patient_state` is empty or no documents are retrieved for a specific query, the agent automatically "auto-transitions" to MCP. This ensures the clinician always receives an answer (from general medical knowledge) even if the local patient record is silent.
3.  **Intent Whitelisting:** The router maintains a whitelist of "RAG-Supported" intents (Summary, Medication, Diagnosis). If a query falls outside this list (categorized as `UNKNOWN` or `GENERAL`), the state machine defaults to the external `mcp_search` node to ensure clinical groundedness.

**2. Choices & Tradeoffs**
*   **LangGraph vs. AutoGPT/BabyAGI:** We chose **LangGraph** for its explicit state control and deterministic routing capability. Clinical environments require predictable, repeatable workflows ("State Machines"), not the open-ended "infinite loops" common in autonomous agent frameworks.
*   **Separation of Concerns:** The `IntentClassifier` is a specialized, lightweight heuristic (or small LLM call) separate from the heavy `generate_response` model. This reduces latency and cost for simple queries.

**3. Configurable Parameters**
*   **`intent_confidence_threshold`**: (Default: 0.70) Confidence score required to auto-route. Below this, the system defaults to a safe fallback (usually broad search).
*   **MCP Protocol Safety Policies:** Hard-coded allowed/forbidden outputs for drug queries to prevent the model from generating dangerous dosing instructions (e.g., `max_tokens` caps, strict "No Dosing" system prompts).

#### **B. RAG Infrastructure (Retrieval-Augmented Generation)**
The RAG layer handles the ingestion, indexing, and semantic retrieval of patient data.

**1. Architecture & Components**
*   **Indexing Pipeline (`DocumentBuilder`):**
    *   **Atomic Indexing:** Instead of chunking arbitrary text windows, the system indexes **Clinical Events**. A single `ClinicalDocument` corresponds 1:1 with a FHIR resource (Encounter, Observation, etc.).
    *   **Content Strategy:** `content_primary` (display text) and `content_details` (context) are combined for embedding but stored separately for UI rendering.
    *   **Field-Level Metadata:** Boolean flags (`is_diagnosis`, `is_medication`) are pre-computed during ingestion to enable $O(1)$ filtering during retrieval.
*   **Retrieval Logic (`MedGemmaRAG`):**
    *   **Vector Backend:** Qdrant with HNSW index and Scalar Quantization (`int8`).
    *   **Embedding:** `search_params` use the `lokeshch19/ModernPubMedBERT` model (768-D).
    *   **Filtering:** Filters are applied *during* search (Pre-filtering), not after. `FieldCondition(key="patient_id", match=MatchValue(value=pid))` ensures we scan only the relevant patient's manifold.
*   **Context Construction:**
    *   Retrieved nodes are re-sorted chronologically (not by similarity score) before being presented to the LLM. This preserves the narrative flow essential for longitudinal reasoning.

**2. Choices & Tradeoffs**
*   **Event-Based vs. Chunk-Based Indexing:** Event-based indexing preserves clinical context (e.g., "This lab result belongs to *this* visit"). The tradeoff is that extremely long notes must be truncated or summarized *before* ingestion to fit within the embedding model's 512-token limit.
*   **Pre-Filtering vs. Post-Filtering:** We strictly use **Pre-Filtering** in Qdrant. Post-filtering (retrieving top-k then filtering by patient) is performant but statistically dangerous; a patient with few records might have zero hits in the global top-k, leading to false negatives.

**3. Configurable Parameters**
*   **`top_k`**: (Default: 5) Number of documents to retrieve. Configurable per query via the UI slider.
*   **`embedding_model`**: Configured in `src/shared/config.py`.
*   **`context_window_size`**: Implicitly controlled by the number of retrieved docs. The system currently targets ~2-3k tokens of context.

#### **C. MCP Service (Model Context Protocol)**
The MCP service acts as the bridge to the external world, adhering to the "FastMCP" standard for tool interoperability.

**1. Architecture & Components**
*   **Router Architecture (`mcps/router.py`):**
    *   **Guardrails:** A regex-based safety layer that instantly blocks pseudoscience queries (Class G).
    *   **Classification Node:** A specialized LLM call (Llama 3.3 70B via Groq) that maps user queries to 7 rigid categories (A-G).
    *   **Search Adaptation:**
        *   **Class C (Interactions):** Routes to `OpenFDA` API.
        *   **Class D (Guidelines):** Routes to `PubMed` search.
        *   **Class B (Ref Ranges):** Routes to `MedlinePlus`.
*   **Summarizer Node:** A second LLM pass that compresses raw HTML/JSON responses into a 2-3 sentence "Evidence Nugget" before returning it to the main agent.
*   **Transport Layer:** Uses **Server-Sent Events (SSE)** for streaming responses, allowing integration with any MCP-compliant client (VS Code, Claude Desktop, or our internal Agent).

**2. Choices & Tradeoffs**
*   **Decoupled Microservice:** Running MCP as a separate service on port 8002 allows it to be scaled independently. The heavy lifting of external scraping and summarization doesn't block the main application thread.
*   **Deterministic Adapters:** We enforce strict schema validation on external APIs. For example, the `OpenFDA` adapter manually parses JSON rather than letting an LLM hallucinate the structure. The tradeoff is higher maintenance when external API schemas change.

*   **`LLM_API_BASE`**: Configurable endpoint for the classification/summarization models (supporting Groq, OpenAI, or local Llama.cpp).

### 19. Evaluation & Benchmarks
To ensure clinical safety and operational readiness, the system is subjected to a rigorous evaluation framework. We measure three core dimensions: **Retrieval Accuracy**, **System Latency**, and **Generation Faithfulness**.

#### **A. Metric Selection & Rationale**
We chose these specific metrics to reflect the safety-critical nature of clinical AI:

**1. Safety in Retrieval: Recall@K**
*   **Definition:** In medicine, *omission is more dangerous than noise*. A high Recall ensures that the system doesn't "overlook" a critical allergy, a past surgical history, or a subtle trend in lab results hidden in the longitudinal record.
*   **Equation:**
    $$Recall@K = \frac{|Relevant \cap Retrieved_K|}{|Relevant|}$$
*   **Safety Threshold:** We measure how many of the "Ground Truth" expert-mapped nodes are present in the top-K chunks retrieved by the vector engine. If a critical node (e.g., an allergy) is ranked at #11 and we only pull Top-10, that is a **Safety Violation**.

**2. Safety in Synthesis: MRR & Faithfulness**
*   **MRR (Mean Reciprocal Rank):** Measures how high the first relevant clinical node appears. High MRR ensures the "Context Assembly" layer places the most relevant facts first in the LLM's attention span, reducing "lost-in-the-middle" reasoning errors.
*   **Equation:**
    $$MRR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{rank_i}$$
*   **Faithfulness Score:** A binary verification of whether every clinical claim made by the model is backed by a physically present citation in the retrieved context. 
*   **Equation:**
    $$Faithfulness = \frac{\sum_{c \in Claims} \mathbb{1}(\text{supported}(c))}{|Claims|}$$
    Where $\mathbb{1}(\text{supported}(c))$ is 1 if the claim is verbatim or semantically supported by the cited EHR node, and 0 otherwise.

**3. Operational Safety: Latency P95**
*   **Definition:** If a system is too slow (e.g., >30s for a simple query), clinicians may skip the verification step or bypass the system entirely. We target sub-second latencies for the RAG pipeline to maintain clinical trust and usability.

#### **B. Test Cases for Safety**
The evaluation is performed against a representative longitudinal case (Mycoplasma Pneumonia) with 10 clinical nodes. The **Safety Column** in our benchmarks specifically aggregates queries that verify the system's ability to handle high-stakes information:

1.  **Safety Verification (Allergy/Adverse Events):** *"What differential diagnoses were considered and why?"* (Checks if the system catches the transition from Bronchitis to Atypical Pneumonia while respecting the penicillin allergy context).
2.  **Trend Analysis:** *"What was the treatment progression and its effectiveness?"* (Verifies that the system identifies the failure of Amoxicillin and the subsequent success of Azithromycin).
3.  **Diagnosis Tracking:** *"How has the patient's diagnosis evolved over time?"* (Ensures no "diagnostic anchoring" by retrieving the full evolution from provisional to final findings).

#### **C. Test Implementation & Sample Workflow**
The evaluation suite is implemented as a set of deterministic Python scripts:

**1. Retrieval Benchmarking (`evaluate_retrieval_recall.py`)**
*   **Sample:** For the query *"Does the patient have any allergies?"*, the ground truth maps to `node-allergy-001`. The test checks if `node-allergy-001` is one of the top results returned by Qdrant.

**2. Faithfulness Auditing (`evaluate_faithfulness.py`)**
*   **Sample Workflow:**
    1.  **Extraction:** It parses the `ClinicalResponse` object to extract every claim (e.g., *"Patient switched to Azithromycin"*) and its associated `source_node_ids` (e.g., `[enc-f4ce6b6f]`).
    2.  **Verification:** It fetches the original TOON text for `[enc-f4ce6b6f]`. It runs a semantic alignment check: *Does the EHR node mention Azithromycin?* If it doesn't, the **Faithfulness Score** drops, and a **Hallucination Alert** is logged.
