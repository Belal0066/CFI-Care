Authentication in CFI-Care is delegated entirely to Keycloak, an open-source Identity and Access Management server that implements the OpenID Connect (OIDC) protocol on top of OAuth 2.0. This approach means the mobile app never handles or stores user credentials , it only deals with tokens issued by Keycloak after the user authenticates.

\subsubsection{Image Quality Detection — Laplacian Variance}
After any image is picked from the gallery or camera, ImageQualityService.computeBlurScore() runs automatically. The algorithm to compute if the image or the scanned photo is blurry or not.

\begin{enumerate}
    \item Convert to grayscale to reduce each pixel to a single value and removes colour noise that could interfere with the edge detection
    \item Computes the variance of all Laplacian responses
A high variance means many sharp edges (a clear image). A low variance means smooth, uniform regions ( a blurry image).
    \item The threshold is set at 80.0: any score below this triggers an orange warning banner in the UI: "Image looks blurry. Try retaking or enhance it."
    
\end{enumerate}
\subsubsection{Magic Filter}
If the image is flagged as blurry (or the user simply wants better quality), the Magic Filter button applies a 6-step document enhancement pipeline :

\begin{table}[h]
\centering
\caption{Image Preprocessing Pipeline}
\label{tab:image_preprocessing}
\begin{tabular}{|c|p{4cm}|p{8cm}|}
\hline
\textbf{Step} & \textbf{Operation} & \textbf{Purpose} \\ \hline
1 & Grayscale & Removes colour noise and reduces the processing space. \\ \hline

2 & Percentile histogram stretch (2\%--98\%) & Corrects uneven lighting while preserving image details without binarization. \\ \hline

3 & Unsharp mask (radius 1, amount 2.5) & Enhances text edges while maintaining gradient information. \\ \hline

4 & 8-connected Laplacian convolution ([-1,-1,-1,-1,9,-1,-1,-1,-1]) & Sharpens both horizontal, vertical, and diagonal text strokes. \\ \hline

5 & S-curve contrast boost (factor 1.5) & Increases contrast by pushing the paper background toward white and the ink toward black. \\ \hline

6 & Auto-invert check & If more than 50\% of pixels are dark, the image is inverted to ensure black text on a white background. \\ \hline
\end{tabular}
\end{table}
The enhanced image is saved as a new file (enhanced\_FileName) and the blur score is re-computed on the result so the warning clears if enhancement succeeded.
\subsubsection{Spirit Level}
One of the most common problems with phone-based document scanning is perspective distortion, when the phone is held at an angle over the document, the resulting image is trapezoid-shaped rather than rectangular, making text harder to read and OCR less accurate. To address this, the CFI-Care scanner includes a real-time spirit level built using the device's accelerometer.


\textbf{How It Works}

The sensors\_plus \cite{sensors_plus} package provides a continuous stream of accelerometer events. The scanner subscribes to this stream in \textbf{\_initSensors()}.

\begin{itemize}
    \item The accelerometer reports gravitational force in m/s² along three axes. When the phone is held perfectly flat and parallel to a surface, both x and y approach 0 and only z carries the full gravitational value (~9.8). The threshold of 0.7 on both axes was chosen experimentally to give a comfortable tolerance — the phone does not need to be perfectly flat, just reasonably aligned.
    \item The bubble's position is a direct mapping of the accelerometer's x and y values . When the phone tilts right, the bubble moves right. When it tilts forward, it moves down, exactly like a physical spirit level. The bubble and its containing ring turn green when the phone is level and red when it is not.
\end{itemize}

\subsection{Clean Architecture in the Mobile Application}

To ensure a scalable, maintainable, and testable codebase for the patient
mobile application, this project adopts principles of Clean Architecture.

Clean Architecture is a layered software design paradigm that promotes clear
separation of concerns, dependency management, and modularization of
application logic. The fundamental goal of this approach is to isolate core
business rules from implementation details and platform-specific frameworks,
thereby improving long-term maintainability and facilitating unit testing
\cite{clean_arch_flutter}.

According to the Flutter documentation on application architecture,
well-structured applications organize code into logical layers that separate
the user interface, application logic, and data handling. The documentation
emphasizes the importance of isolating state management, dependency injection,
and data access concerns to support growth and complexity in larger
applications \cite{flutter_architecture}.

As illustrated in Figure~\ref{fig:clean-architecture}, the the application is
structured into three principal layers: the presentation layer, the domain
layer, and the data layer. Each layer has a distinct responsibility and
communicates with adjacent layers through abstract interfaces, ensuring that
dependencies always point inward toward business logic rather than outward
toward infrastructure or frameworks \cite{clean_arch_flutter}.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\textwidth]{Mobile/Images/Clean-Architecture-Flutter-Diagram-Reso-Coder.png}
    \caption{Layered Clean Architecture adopted in the mobile application}
    \label{fig:clean-architecture}
\end{figure}

\subsection{Layered Structure}

\paragraph{Presentation Layer}
This outermost layer contains code that directly interacts with the user
interface. In the context of this Flutter application, it includes widgets,
screens, routing logic, and Riverpod providers to manage application state when
implemented. The presentation layer orchestrates the flow of data from use
cases in the domain layer to the UI and captures user interactions for
processing. Presentation logic is kept distinct from business rules and data
access to avoid tightly coupling UI changes with core system logic
\cite{clean_arch_flutter}.

\paragraph{Domain Layer}
The domain layer encapsulates the core business logic and entities of the
system. It is independent of Flutter or any external dependencies. This layer
defines use cases that represent application-specific operations, such as
requesting document access or scheduling appointments, and serves as the
central coordinator of business rules. The domain layer’s independence from
external libraries and frameworks enhances testability and ensures that
business logic can be validated in isolation \cite{clean_arch_flutter}.

\paragraph{Data Layer}
The data layer is responsible for integrating with external systems, including
APIs, local storage, and the backend FHIR server. It provides implementations
of repository interfaces defined in the domain layer and manages data
transformation between network responses, local models, and domain entities.
The layered separation ensures that external dependencies do not leak into the
domain or presentation layers \cite{clean_arch_flutter}.

\subsection{Centralized Runtime Permission Handling}

To ensure a secure and seamless interaction with device hardware, the
application implements a centralized asynchronous mechanism for managing
runtime permissions. This approach abstracts the complexity of the
\texttt{permission\_handler} library and follows established patterns for
robust permission management \cite{anthony2025permissions}. The function
\texttt{handlePermission} provides a unified interface for requesting access to
sensitive resources such as the camera, storage, or microphone.

The function operates as a \texttt{Future<bool>}, returning a boolean value to
indicate the success or failure of the authorization process. Upon invocation,
the function executes the following logic flow:

\begin{enumerate}
    \item \textbf{Asynchronous Request:} It initiates a request to the underlying operating system using \texttt{permission.request()}. The execution yields until the user interacts with the system dialog or the operating system returns the current status.

    \item \textbf{Status Evaluation:} The returned \texttt{PermissionStatus} is evaluated against standard authorization states:
          \begin{itemize}
              \item \textbf{Granted:} If the user approves the request (\texttt{isGranted}), the function immediately returns \texttt{true}, allowing the calling process to proceed.
              \item \textbf{Permanently Denied:} If the permission is flagged as \texttt{isPermanentlyDenied} (a state where the operating system suppresses further prompts due to repeated denials), the system intervenes to prevent a silent failure. It displays a toast notification instructing the user to enable the permission manually and invokes \texttt{openAppSettings()} to redirect the user to the device’s settings menu.
              \item \textbf{Denied:} In cases of a standard denial, a feedback message is displayed via \texttt{Fluttertoast} to inform the user of the restriction, and the function returns \texttt{false}.
          \end{itemize}
\end{enumerate}

By encapsulating this logic, the system ensures that permission failures are
handled gracefully, guiding users through recovery steps when necessary rather
than causing application crashes or unresponsive features. The implementation
of this logic is demonstrated in Listing \ref{lst:perm_logic}. \newpage
\begin{lstlisting}[
    language=Java, 
    basicstyle=\ttfamily\footnotesize, 
    frame=single, 
    breaklines=true, 
    caption={Asynchronous Permission Handling Function}, 
    label={lst:perm_logic}
]
import 'package:permission_handler/permission_handler.dart';
import 'package:fluttertoast/fluttertoast.dart';

Future<bool> handlePermission(
  Permission permission,
  String name,
) async {
  final status = await permission.request();

  // Case 1: Permission Granted
  if (status.isGranted) {
    return true;
  }

  // Case 2: Permanently Denied (Requires Settings)
  if (status.isPermanentlyDenied) {
    Fluttertoast.showToast(
      msg: '$name permission permanently denied. Enable it in settings.',
    );
    openAppSettings();
    return false;
  }

  // Case 3: Standard Denial
  Fluttertoast.showToast(msg: '$name permission denied');
  return false;
}
\end{lstlisting}

\begin{itemize}
    \item \textbf{Contextual Permission Requests: }To avoid overwhelming the user and to establish context, the application rejects the traditional ``up-front'' permission model (where all permissions are requested at launch). Instead, a \textit{Contextual Request} pattern is employed. Permissions are only requested at the specific moment a feature is invoked. For example, access to the \texttt{Camera} is requested solely when the user attempts to scan a medical report.
          % and access to \texttt{Location} is requested only when the user initiates the ``Find Nearby Clinics'' feature.\cite{daydreamsoft2025permissions}
    \item \textbf{Transparent Rationale and Trust Building: } In compliance with privacy best practices, the application explains the ``Why'' before the ``How.'' Prior to triggering the system permission dialog, the application presents a custom UI explanation detailing exactly why a specific permission is needed and how it benefits the user. This transparency is critical in a healthcare context, increasing the likelihood of approval and reinforcing the patient's understanding that their data is being used strictly for medical management.\cite{daydreamsoft2025permissions}
    \item \textbf{User Agency and Graceful Degradation: } The system is designed to respect user choices without compromising the core functionality of the application. If a user denies a non-critical permission, the app enters a state of \textit{Graceful Degradation}.
          % For instance, if access to the \texttt{Calendar} is denied, the appointment booking feature remains active, but the automatic synchronization with the user's personal schedule is disabled. 

          The application avoids repetitive prompting (``nagging''), ensuring a
          respectful user experience. \cite{daydreamsoft2025permissions}

    \item \textbf{Comprehensive State Handling: }The application logic accounts for the full lifecycle of permission states, ensuring stability across different scenarios\cite{daydreamsoft2025permissions}\cite{boudanes2024permissions}:
          \begin{itemize}
              \item \textbf{Granted:} The feature proceeds immediately.
              \item \textbf{Denied:} The feature is disabled, and the user is informed of the limitation.
              \item \textbf{Permanently Denied:} In cases where the user has selected ``Don't ask again,'' the application detects this state and provides a subtle option to guide the user to the system \texttt{App Settings} menu for manual enablement, should they choose to do so later.
          \end{itemize}

The Android Manifest files are configured to declare only the absolute minimum permissions required for functionality, adhering to the principle of \textit{Least Privilege}. This minimizes the security surface area and ensures compliance with modern mobile operating system standards.

\end{itemize}

\section{FCM Push Notifications}
The system uses Firebase Cloud Messaging (FCM) to deliver real-time push notifications from the Node.js backend to the Flutter mobile app. FCM acts as a broker: the backend never sends a message directly to a device — it sends a message to Google's FCM servers, which deliver it to the target device using its unique FCM token.
\subsection{How It Works}
\subsubsection{Part 1 — Token Registration}
\begin{itemize}
    \item Before any notification can be sent, the backend must know the device's Firebase Cloud Messaging (FCM) token.

    \item On the Flutter side, the application calls FirebaseMessaging.instance.getToken()
    to obtain the device's unique FCM token.

    \item The token is then sent to the backend through:
    \begin{verbatim}
POST /FCM/fcm-token
{
    "fcmToken": "abc123"
}
    \end{verbatim}

    \item Token rotation is handled automatically. Whenever Firebase generates a new token, the updated value is sent again to the same endpoint.
\end{itemize}
\subsubsection{Part 2 — The Shared Sender Utility}
All notifications go through one private function :


\begin{itemize}
    \item Before sending a notification, the backend retrieves the recipient's FCM token from Redis using the user's identifier.

    \item If no token is found, the notification is skipped because the user does not have a registered device.

    \item The backend then sends a Firebase Cloud Messaging (FCM) message containing both notification and data payloads.

    \item Notifications are sent with high priority to ensure timely delivery.
    \item Each notification message consists of two components:
    \begin{itemize}
        \item \textbf{Notification Payload}: Contains the user-visible content, including the notification title and body displayed in the operating system's notification tray.
        
        \item \textbf{Data Payload}: Contains structured key--value pairs processed by the Flutter application. The most important field is \texttt{type}, which identifies the notification category and determines the action that the application should perform upon receiving the message.
    \end{itemize}
\end{itemize}

Upon receiving the notification, the Flutter application refreshes the

    \item \textbf{Session Initiation:} While doctors primarily use the Web Interface, their actions directly trigger updates on the mobile app. A doctor initiates a "New Encounter Node" in the patient's history tree during a visit.
    \item \textbf{Access Requests:} Doctors request permission to view a patient's historical records. If granted "Write" access, they can add new diagnoses and prescriptions to the encounter node.
    \item \textbf{Limitation:} Doctors strictly cannot book appointments; this function is reserved for patients and their families to prevent conflict of interest or scheduling errors.
\end{itemize}
\textbf{Benefits:}
\begin{itemize}
    \item \textbf{Informed Decision Making:} Instant access to a comprehensive medical history allows for more accurate diagnoses.
    \item \textbf{Efficiency:} Reduces time spent interviewing patients for past medical details, allowing more focus on current treatment.
\end{itemize}

\section{My Profile Update}
Figure \ref{fig:My Profile Use Case} details the data consistency mechanism.
\begin{enumerate}
    \item \textbf{Local Commit:} When the user saves changes, the application first updates the local SQLite database. This ensures the user interface is responsive and works even with poor internet connectivity.
    \item \textbf{Remote Synchronization:} Immediately following the local commit, the application initiates an asynchronous API call to update the backend server.
    \item \textbf{Consistency Check:} Upon a successful server response, the application confirms the synchronization status, ensuring the patient's data is consistent across all platforms.
\end{enumerate}
