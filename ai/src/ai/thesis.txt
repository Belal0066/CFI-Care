Q1: How does the confidence score work?
────────────────────────────────────────

The system implements a **Multi-Layer Confidence Scoring** framework that
quantifies reliability across four independent pipeline stages, combined into
a single weighted index. Each layer is computed at a specific LangGraph node
and propagated through `ClinicalAgentState`.

FORMULA:
    C_total = w1 * C_routing + w2 * C_retrieval + w3 * C_generation + w4 * C_validation

Default weights (from `src/retrieval/config.py:43-46`):
    w_routing  = 0.15   (intent classification accuracy)
    w_retrieval = 0.25   (evidence quality from vector search)
    w_generation = 0.30   (LLM token-level certainty)
    w_validation = 0.30   (post-generation citation audit)

────────────────────────────────────────
LAYER 1: Intent Routing Confidence (C_routing)
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:347-384` (classify_intent node)

- The `IntentClassifier` (rule-based regex, 10 clinical intents + UNKNOWN)
  returns a tuple (intent, confidence).
- The confidence is the match quality score from the classifier.
- Stored as `intent_confidence` in agent state.
- Also controls routing: if C_routing < 0.70 (routing_fallback_threshold),
  the system falls back to broad RAG instead of MCP to avoid hallucinating
  from internet sources (`workflow.py:124-126`).

────────────────────────────────────────
LAYER 2: Retrieval Context Alignment (C_retrieval)
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:404-526` (retrieve_patient_context node)

- Primary path: `HybridRetriever.search_by_encounter()` returns
  `EncounterGroup` objects with RRF-fused scores.
- C_retrieval = max(encounter_scores) — the highest-ranked encounter group's
  relevance score.
- Also computed: `retrieval_avg_top3` — average of top 3 scores, used to
  detect `has_insufficient_data` when below gatekeeper threshold (0.15).
- RRF normalization (`confidence.py:22-47`):
    max_possible = 2 / (k + 1)    where k = 60 (rank constant)
    normalized_score = raw_rrf / max_possible
- This maps the unbounded RRF score to [0, 1].

────────────────────────────────────────
LAYER 3: LLM Generation Token Confidence (C_generation)
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:1128-1152` (generate_response node)
        `src/agent/confidence.py:50-67` (compute_generation_confidence)

- The LLM (MedGemma) is called with `logprobs=True`, which returns the
  log-probability of each generated token.
- Computed as: C_generation = exp(mean(token_logprobs))
- This is a geometric mean of token probabilities, mapping from log-space
  (-inf, 0] to probability space (0, 1].
- Intuition: if the LLM is confident (each token ~1.0 probability), the mean
  logprob is near 0 and exp(0) = 1.0. If uncertain (token probs ~0.1), the
  mean logprob is ~-2.3 and exp(-2.3) ≈ 0.1.
- Fallback: if logprobs unavailable, uses self-consistency agreement score.

────────────────────────────────────────
LAYER 4: Post-Generation Validation (C_validation)
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:292-345` (audit_claims node)
        `src/agent/confidence.py:70-87` (compute_validation_confidence)

- After generation, the `audit_claims` node validates every citation in the
  response against the actual retrieved document IDs.
- For each claim's `source_node_ids`, it checks whether each ID exists in
  the valid set of encounter/chunk IDs from retrieval.
- C_validation = supported_claims / total_claims
- If all claims cite valid documents → 1.0. If 3 of 5 are valid → 0.6.
- Failed audits trigger a self-correction loop: the generate node is re-invoked
  with corrective feedback injected (`inject_audit_feedback()`), up to
  MAX_AUDIT_RETRIES = 2.

────────────────────────────────────────
UNION AND OUTPUT
────────────────────────────────────────
Source: `src/agent/graph/workflow.py:25-65` (_compute_confidence node)

- Runs as the final node before END.
- Calls `compute_overall_confidence()` with all four layer values.
- Appends a formatted confidence block to the response text:
    *Intent Routing: 0.85 (High)*
    *Evidence Quality: 0.72 (Medium)*
    *Response Consistency: 0.91 (High)*
    *Factual Verification: 1.00 (High)*
    *Overall: 0.87 (High)*
- Labels: Low (< 0.50), Medium (< 0.75), High (>= 0.75).

────────────────────────────────────────
WHY THIS MATTERS
────────────────────────────────────────
The multi-layer design provides:
1.  diagnosability — a low C_routing means the intent was misclassified; a
    low C_validation means the LLM hallucinated citations. Clinicians see
    exactly which stage degraded.
2.  graceful degradation — if retrieval returns weak results (C_retrieval < 0.15),
    the system flags `has_insufficient_data` and can refuse to answer rather
    than synthesize from poor evidence.
3.  self-correction — the audit→generate loop catches citation errors at
    generation time, not at clinical use time.
4.  interpretability — the confidence block is appended to every response,
    making reliability transparent to the end user without requiring
    separate instrumentation.

Q2: How do you prevent hallucinations?
────────────────────────────────────────

The system uses a **defense-in-depth** strategy with six independent layers,
each targeting a different hallucination vector. No single layer is sufficient;
they overlap to catch failures at different pipeline stages.

────────────────────────────────────────
LAYER 1: Bounded Deterministic Reasoning (Pre-Generation)
────────────────────────────────────────
Source: `src/agent/clinical_reasoning.py:130-149` (ClinicalReasoner)

The `ClinicalReasoner` operates under hard constraints enforced at the class
level:

    class ClinicalReasoner:
        """
        Operating Constraints:
        1. Reason ONLY over retrieved documents
        2. NO external medical knowledge
        3. NO speculation beyond documented facts
        4. ALL claims must be cited
        """

- The reasoner receives a `RetrievalContext` containing ONLY documents returned
  by the vector search. It has no access to the LLM's parametric knowledge
  during this phase.
- Every reasoning method (reason_for_summary, reason_for_diagnosis,
  reason_for_medication, etc.) constructs a `ClinicalResponse` where each claim
  is a `CitedClaim` with mandatory `source_node_ids`.
- Data sufficiency is checked BEFORE reasoning (`_check_data_sufficiency()`):
  if no diagnosis documents exist for a diagnosis query, it returns
  `has_insufficient_data=True` with confidence="Low" instead of guessing.

────────────────────────────────────────
LAYER 2: Citation Enforcement (Structural)
────────────────────────────────────────
Source: `src/agent/clinical_reasoning.py:27-45` (CitedClaim)

The `CitedClaim` Pydantic model enforces citations at the schema level:

    class CitedClaim(BaseModel):
        claim: str
        source_node_ids: List[str]  # MANDATORY — no empty lists allowed

- The LLM generates text, but the deterministic `ClinicalReasoner` wraps every
  statement in a `CitedClaim` before it reaches the response.
- The `source_node_ids` field is `List[str]` with no default — the constructor
  will reject any claim without at least one citation.
- This means a claim like "Patient has pneumonia" without a reference document
  ID is structurally impossible in the `ClinicalResponse`.

────────────────────────────────────────
LAYER 3: Post-Generation Citation Audit (Validation)
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:292-345` (audit_claims node)
        `src/agent/auditor.py:12-129` (ClaimAuditor)

After the LLM generates the final response, the `audit_claims` node performs
a mechanical verification:

    FOR each claim in clinical_response.claims:
        FOR each cited_id in claim.source_node_ids:
            IF cited_id NOT IN valid_ids from retrieval:
                → audit failure

- `valid_ids` is built from the actual `encounter_groups` returned by
  retrieval — it is the ground truth set of what was retrieved.
- Any citation referencing a non-existent document ID is a failure.
- The audit returns `validation_confidence = supported_claims / total_claims`.
- This catches the most dangerous hallucination type: fabricated citations
  (the LLM invents a source that doesn't exist).

────────────────────────────────────────
LAYER 4: Self-Correction Loop (Repair)
────────────────────────────────────────
Source: `src/agent/graph/workflow.py:168-194` (route_after_audit)
        `src/agent/graph/nodes.py:902-911` (inject_audit_feedback)

When the audit fails, the system does NOT return the faulty response. Instead:

    audit_claims → audit_passed=False → route_after_audit → generate (retry)
                                                         ↑          |
                                                         |__________|

- The `inject_audit_feedback()` function builds a corrective prompt fragment:

    "**CORRECTION REQUIRED — Citation Audit Failed:**\n"
    "- Claim 0 cites non-existent ID: xyz\n"
    "Fix all citations so every source_node_id references a valid document."

- This feedback is injected into the user prompt for the regeneration call.
- The LLM sees its own errors and is instructed to fix them.
- Maximum 2 retries (`MAX_AUDIT_RETRIES = 2`), then the system finishes with
  whatever it has and reports the failure via C_validation.

────────────────────────────────────────
LAYER 5: MCP Safety Guardrails (Internet Evidence)
────────────────────────────────────────
Source: `mcps/router.py:45-49` (guardrail_node)
        `src/agent/graph/nodes.py:47-120` (MCP_QUESTION_TYPES)

For internet-sourced evidence (PubMed, OpenFDA), two safety mechanisms operate:

(a) Pseudoscience filter — the MCP `guardrail_node` blocks queries containing
    keywords like "homeopathy", "chakra", "crystal healing" by returning
    classification="G" (Insufficient Evidence/Harmful), which terminates the
    MCP pipeline before any retrieval occurs.

(b) Domain-specific safety policies — each MCP question type
    (drug_contraindications, drug_interactions, drug_side_effects,
    treatment_guidelines) has a policy dict with:
    - `allowed_output`: what the LLM may include in its response
    - `forbidden_output`: what it must NOT include (e.g., "dosing",
      "treatment protocol" for contraindication queries)
    - `system_prompt`: constrains the LLM to only answer within the scope

    Example (drug_contraindications):
        forbidden_output: ["dosing", "treatment protocol", "diagnostic criteria"]
        → prevents the LLM from hallucinating treatment advice when asked
          about contraindications.

────────────────────────────────────────
LAYER 6: Confidence-Gated Routing (Prevention)
────────────────────────────────────────
Source: `src/agent/graph/workflow.py:122-131` (route_intent)

    if confidence < CONFIDENCE_THRESHOLD:  # 0.70
        return "rag_retrieve"  # Fall back to local patient data

- When intent classification confidence is low, the system avoids the MCP
  (internet) path entirely and routes to local RAG instead.
- Rationale: a misclassified query sent to PubMed could retrieve irrelevant
  literature, which the LLM would then synthesize into a plausible-sounding
  but incorrect answer (hallucination via irrelevant context).
- Broad RAG over local patient data is safer — if the data isn't there, the
  system returns `has_insufficient_data=True` instead of fabricating.

────────────────────────────────────────
SUMMARY: DEFENSE-IN-DEPTH MAP
────────────────────────────────────────

    Hallucination Type          │ Layer That Catches It
    ────────────────────────────┼──────────────────────────────────
    Fabricated citations        │ Layer 3 (Citation Audit)
    Invented clinical facts     │ Layer 1 (Bounded Reasoning)
    Claims without evidence     │ Layer 2 (CitedClaim schema)
    Incorrect citations         │ Layer 3 + Layer 4 (Audit + Retry)
    Pseudoscience / harmful     │ Layer 5a (Guardrail)
    Domain leakage in drug Qs   │ Layer 5b (Safety Policies)
    Irrelevant context synthesis│ Layer 6 (Confidence Gating)
    Confident but wrong output  │ C_generation (token logprobs)

Q3: How do citations work?
────────────────────────────────────────

Citations follow a **full-lifecycle** design: every clinical fact traced from
FHIR ingestion through vector storage, retrieval, reasoning, generation, and
post-generation audit. The system guarantees that every claim in the final
response maps back to a specific document ID that was actually retrieved.

────────────────────────────────────────
STAGE 1: ID Assignment at Ingestion
────────────────────────────────────────
Source: `src/ingestion/service.py:113-193` (IngestionService.ingest_resource)

Each clinical node enters the system with a source `id` from the FHIR/JSON
input. During ingestion:

    payload = {
        "id": chunk.chunk_id,           # Unique chunk identifier
        "parent_node_id": node_id,       # Original clinical event ID
        "patient_id": patient_id_global, # Patient/EOC identifier
        "toon_content": chunk.text,      # TOON-normalized text
        "is_diagnosis": is_diag,         # Boolean filter flags
        "is_medication": is_med,
        "is_allergy": is_allergy,
        ...
    }

- `node_id` is the canonical citation target — it represents one clinical
  event (e.g., "Encounter 2024-01-15: Chest X-Ray showing pneumonia").
- Long documents are chunked (`DocumentChunker`, 400 chars, 50 overlap), but
  every chunk retains `parent_node_id` pointing to the original node.
- The `anchor_id` in downstream retrieval always resolves to `node_id`.

────────────────────────────────────────
STAGE 2: Hybrid Retrieval Returns Anchored Results
────────────────────────────────────────
Source: `src/retrieval/service.py:211-227` (HybridRetriever.search)

The `HybridRetriever` performs Qdrant dense+sparse search and returns
`RetrievedContext` objects:

    RetrievedContext(
        anchor_id=str(original_id),   # ← node_id from payload
        anchor_content=toon_content,   # The clinical text
        score=rrf_score,              # Hybrid relevance score
        parent_node_id=...,           # For encounter grouping
        father_id=...,                # Graph relationship
        date_issued=...,              # Temporal metadata
    )

- `anchor_id` is the stable citation key. It is extracted from
  `hit.payload.get("id", str(hit.id))` — the original node ID, NOT the
  chunk ID.
- This ensures that even when a document is chunked for embedding, all chunks
  resolve to the same parent citation ID.

────────────────────────────────────────
STAGE 3: Encounter-Level Grouping
────────────────────────────────────────
Source: `src/retrieval/service.py:234-304` (HybridRetriever.search_by_encounter)

Retrieved chunks are grouped by `parent_node_id` into `EncounterGroup`:

    EncounterGroup(
        encounter_id=enc_id,    # = parent_node_id
        score=encounter_score,  # max(chunk_scores) + count_bonus
        chunks=[...],           # List[RetrievedContext]
        father_id=...,
        date_issued=...,
    )

- The `encounter_id` becomes the top-level citation unit in the response.
- A single clinical event with multiple chunks produces ONE encounter group,
  preventing duplicate citations for the same event.

────────────────────────────────────────
STAGE 4: Deterministic Reasoning Attaches Citations
────────────────────────────────────────
Source: `src/agent/clinical_reasoning.py:27-45` (CitedClaim)
        `src/agent/clinical_reasoning.py:130-149` (ClinicalReasoner)

The `ClinicalReasoner` does NOT use the LLM for citation attachment. Instead,
it deterministically constructs `CitedClaim` objects:

    CitedClaim(
        claim="Active diagnosis: Community-Acquired Pneumonia",
        source_node_ids=["enc-003"],   # ← directly from doc.node_id
        temporal_context="2024-01-15"
    )

- Each reasoning method (reason_for_summary, reason_for_diagnosis,
  reason_for_medication, etc.) iterates over `self.context.retrieved_documents`
  and attaches `source_node_ids=[doc.node_id]` for every claim.
- This is a **mechanical** operation — no LLM inference is involved in
  deciding which citation to attach. The citation is the document ID that
  was retrieved.
- `source_node_ids` is `List[str]` with no default — Pydantic will reject
  any claim constructed without at least one citation.

────────────────────────────────────────
STAGE 5: LLM Generation (Citations Injected into Prompt)
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:1092-1155` (generate_response, RAG mode)

The LLM receives the deterministic reasoning output as context:

    user_prompt = f"Query: {query}\n\nClinical Reasoning:\n{explanation}"
    if encounter_context:
        user_prompt += f"\n\nEncounter Context:\n{encounter_context}"

- The `explanation` already contains the cited claims with source_node_ids.
- The `encounter_context` includes the raw TOON content from each encounter.
- The LLM's role is to synthesize a professional narrative FROM the reasoning,
  not to generate new claims. The system prompt enforces:
    "Do NOT add new facts. Stick strictly to the reasoning provided."
- The `CitedClaim` objects are serialized in the clinical_response dict that
  passes through the graph state — the LLM cannot modify them.

────────────────────────────────────────
STAGE 6: Post-Generation Citation Audit
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:292-345` (audit_claims)
        `src/agent/auditor.py:12-129` (ClaimAuditor)

After generation, the `audit_claims` node performs mechanical verification:

    valid_ids = set()
    for eg in encounter_groups:
        valid_ids.add(eg.encounter_id)        # encounter-level IDs
        for chunk in eg.chunks:
            valid_ids.add(chunk.anchor_id)     # chunk-level IDs

    for claim in clinical_resp.claims:
        for cid in claim.source_node_ids:
            if cid not in valid_ids:
                failures.append({
                    "claim_index": i,
                    "cited_id": cid,
                    "message": f"Claim {i} cites non-existent ID: {cid}"
                })

- `valid_ids` is built from the ACTUAL retrieval results — the ground truth.
- Any cited ID not in this set is a fabricated citation.
- The audit also runs `ClaimAuditor._is_evidence_grounded()` which checks
  fuzzy matching (≥50% of key medical terms from the evidence appear in the
  retrieved context text).
- Logical sanity check: confidence > 0.95 with < 2 supporting evidence
  documents triggers a warning.

────────────────────────────────────────
STAGE 7: Self-Correction on Audit Failure
────────────────────────────────────────
Source: `src/agent/graph/workflow.py:168-194` (route_after_audit)

    audit_passed=False → inject_audit_feedback → generate (retry)

- The corrective feedback lists every invalid citation ID.
- The LLM is re-prompted with: "Fix all citations so every source_node_id
  references a valid document."
- Up to 2 retries. After that, the response is returned with C_validation
  reflecting the remaining failures.

────────────────────────────────────────
CITATION FLOW DIAGRAM
────────────────────────────────────────

    FHIR Node (id="enc-003")
         │
         ▼
    Ingestion: chunk + embed + store in Qdrant
    payload.parent_node_id = "enc-003"
         │
         ▼
    Retrieval: HybridRetriever.search()
    RetrievedContext(anchor_id="enc-003", ...)
         │
         ▼
    Encounter Grouping: search_by_encounter()
    EncounterGroup(encounter_id="enc-003", chunks=[...])
         │
         ▼
    Reasoning: ClinicalReasoner.reason_for_diagnosis()
    CitedClaim(source_node_ids=["enc-003"])
         │
         ▼
    Generation: LLM synthesizes narrative FROM reasoning
    (CitedClaims pass through graph state unchanged)
         │
         ▼
    Audit: audit_claims()
    "enc-003" ∈ valid_ids? → PASS / FAIL
         │
         ▼
    Confidence: C_validation = supported / total
         │
         ▼
    Response to clinician with citation block

────────────────────────────────────────
KEY DESIGN DECISIONS
────────────────────────────────────────
1. Citations are DETERMINISTIC, not LLM-generated — the reasoner mechanically
   attaches doc.node_id to every claim. The LLM cannot invent citations.
2. The audit is POST-GENERATION — even if the LLM somehow modifies the
   clinical_response dict, the audit validates against retrieval ground truth.
3. Encounter-level grouping prevents citation deduplication problems — one
   clinical event = one citation unit, regardless of how many chunks it
   produces.
4. The self-correction loop is bounded (2 retries) to prevent infinite loops
   while still giving the LLM a chance to fix its own errors.

Q4: How does the current Agentic RAG work?
────────────────────────────────────────

The Agentic RAG is a **LangGraph StateGraph** that orchestrates the full
pipeline from user query to citation-audited response. It combines local
patient data retrieval (RAG), internet medical evidence (MCP), deterministic
clinical reasoning, and LLM synthesis into a single directed graph with
conditional routing.

────────────────────────────────────────
GRAPH TOPOLOGY
────────────────────────────────────────
Source: `src/agent/graph/workflow.py:68-198`

    ┌──────────┐
    │ classify │  ← Entry point
    └────┬─────┘
         │
    route_intent (conditional)
    ┌────┼──────────┬────────────┐
    │    │          │            │
    ▼    ▼          ▼            ▼
  rag   mcp      visualize     generate
  _retrieve _search             (chat)
    │    │          │
    │    │          │
    ▼    │          │
  reason │          │
    │    │          │
    route_after_    │
    reason (cond.)  │
    ┌────┴───┐      │
    │        │      │
    ▼        ▼      │
  mcp    generate   │
  _search   │       │
    │    ┌───┘       │
    │    │           │
    └────┘           │
         │           │
         ▼           │
    generate ◄───────┘
         │
         ▼
    audit_claims
         │
    route_after_audit (conditional)
    ┌────┴──────────┐
    │               │
    ▼               ▼
  generate     compute_confidence
  (retry)           │
                    ▼
                   END

Nodes: 8 total — classify, rag_retrieve, reason, mcp_search, visualize,
       generate, audit_claims, compute_confidence
Edges: 3 conditional, 5 deterministic

────────────────────────────────────────
STATE SCHEMA (ClinicalAgentState)
────────────────────────────────────────
Source: `src/agent/graph/state.py:5-51`

The graph operates on a single shared state dict (TypedDict):

    messages: List[BaseMessage]           # Full conversation history
    patient_id: str                       # Patient/EOC identifier
    patient_state: Dict                   # Compiled PatientState (active dx, meds, etc.)
    documents: List[ClinicalDocument]     # In-memory RAG documents (fallback)
    intent: str                           # Classified clinical intent
    intent_confidence: float              # Routing confidence (C_routing)
    encounter_groups: List[EncounterGroup] # Retrieved evidence grouped by encounter
    internet_evidence: List[Dict]         # MCP external evidence
    clinical_response: Dict               # Deterministic reasoning output
    needs_drug_check: bool                # Flag: trigger MCP after RAG for drug safety
    audit_passed: bool                    # Citation audit result
    audit_failures: List[Dict]            # Failed citation details
    generation_confidence: float          # Token-level LLM confidence
    validation_confidence: float          # Citation audit confidence
    overall_confidence: float             # Weighted C_total
    mode: str                             # "auto" | "local" | "mcp" | "chat"

Every node reads from and writes to this shared state. No data is passed
via function arguments — the graph runtime manages state propagation.

────────────────────────────────────────
NODE 1: classify_intent
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:347-384`

    Input:  state["messages"][-1].content  (user query)
    Output: intent, intent_confidence, rewritten_query, retrieval_threshold,
            needs_drug_check

- Uses `IntentClassifier` (rule-based regex, 10 clinical intents + UNKNOWN).
- Sets `retrieval_threshold` via `QueryRewriter.determine_retrieval_threshold()`
  (intent-specific: diagnosis=0.15, medication=0.20, etc.).
- Detects drug-safety queries by scanning for keywords ("adverse effect",
  "side effect", "drug risk") and sets `needs_drug_check=True`.
- This flag triggers the hybrid path: RAG first (patient meds) → MCP
  (external drug-safety evidence).

────────────────────────────────────────
NODE 2: retrieve_patient_context
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:404-526`

    Input:  patient_id, prompt, intent, retrieval_threshold
    Output: encounter_groups, retrieval_confidence, retrieval_avg_top3,
            has_insufficient_data

Primary path — Qdrant HybridRetriever:
    hybrid = HybridRetriever()
    encounter_groups = hybrid.search_by_encounter(
        patient_id=patient_id,
        query=prompt,
        threshold=threshold,    # intent-specific
        intent=intent,          # applies Qdrant SHOULD filters
    )

- Embeds query via FastEmbed (dense bge-base-en-v1.5 + sparse SPLADE).
- Qdrant hybrid search with RRF fusion (k=60).
- Groups results by `parent_node_id` into `EncounterGroup` objects.
- Computes retrieval confidence = max(encounter_scores).
- Detects `has_insufficient_data` when avg_top3 < gatekeeper_threshold (0.15).

Fallback path — ContextRetriever (in-memory documents):
    If HybridRetriever fails, falls back to `ContextRetriever` using
    the in-memory `documents` list from session state.

────────────────────────────────────────
NODE 3: run_deterministic_reasoning
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:528-592`

    Input:  encounter_groups, intent, prompt, patient_state
    Output: clinical_response (dict with claims, citations, explanation)

- Flattens `EncounterGroup` chunks into `ClinicalDocument` objects.
- Constructs `RetrievalContext` and `QueryContext`.
- `ClinicalReasoner.reason()` routes to intent-specific method:
    - reason_for_summary()      → timeline + active dx + meds
    - reason_for_diagnosis()    → chronological dx progression
    - reason_for_differential() → dx considered + supporting evidence
    - reason_for_medication()   → med history + allergy warnings
    - reason_for_change_tracking() → temporal comparisons
    - reason_for_trend_analysis()  → trend detection
    - reason_for_timeline()     → full event timeline
    - reason_for_outcome()      → treatment outcomes
    - reason_for_rationale()    → clinical reasoning chain
    - reason_for_allergy()      → allergy + adverse reaction context
- Each method returns a `ClinicalResponse` with `CitedClaim` objects
  containing mandatory `source_node_ids`.
- The LLM is NOT involved in this stage — reasoning is fully deterministic.

────────────────────────────────────────
NODE 4: query_mcp
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:642-891`

    Input:  messages, patient_state, encounter_groups
    Output: internet_evidence (PubMed/OpenFDA results)

Three query construction strategies:

(a) Drug safety queries (drug_contraindications/interactions/side_effects):
    - Extracts actual drug names from RAG encounter groups via regex
      (dose patterns + drug-class suffixes: -pril, -lol, -sartan, etc.)
    - Builds context-enriched query: "{Lisinopril Amlodipine} adverse effects
      renal impairment nephrotoxicity"
    - Deterministic construction (no LLM) to prevent domain leakage.

(b) Treatment guidelines:
    - Passes raw query to MCP (which has its own LLM optimizer).

(c) General queries:
    - Uses LLM to optimize query with conversation context.
    - System prompt requires "SEARCH:" prefix in output.
    - Multiple extraction strategies: SEARCH prefix, entity+intent
      combination, medical+action pattern matching.

WHY "AGENTIC" RAG
────────────────────────────────────────
The system is "agentic" because:

1. AUTONOMOUS ROUTING — the classify node decides which evidence source to
   use (RAG vs MCP vs both) without user intervention.
2. MULTI-SOURCE FUSION — the generate node can combine local patient data
   (RAG) with internet literature (MCP) in a single response.
3. SELF-CORRECTION — the audit→generate loop catches citation errors and
   retries with corrective feedback.
4. CONDITIONAL FLOW — the graph has 3 conditional edges that adapt the
   execution path based on runtime state (intent, confidence, drug-check
   flag, audit result).
5. STATE PROPAGATION — all decisions are recorded in the shared state and
   visible in the confidence block, making the agent's reasoning
   transparent.

Q5: What are the parameters and configs of your RAG, and why did you choose
    them?
────────────────────────────────────────

The RAG pipeline has 5 configuration layers: embedding, chunking, vector
search, retrieval, and generation. Each parameter was chosen to balance
clinical safety, retrieval quality, and latency constraints.

────────────────────────────────────────
1. EMBEDDING MODEL
────────────────────────────────────────
Source: `src/shared/config.py:27-28`
        `src/shared/db_clients.py:47-49`

    Model:       BAAI/bge-base-en-v1.5
    Dimension:   768
    Distance:    COSINE
    Runtime:     FastEmbed CPU (no GPU required)

Why bge-base-en-v1.5:
- Medical domain performance: bge-base achieves MTEB average ~64.0, competitive
  with larger models. It handles medical terminology well because it was
  pre-trained on diverse web corpora that include PubMed abstracts.
- Dimension trade-off: 768-dim is the sweet spot — 384-dim (bge-small) loses
  clinical nuance, 1024-dim (bge-large) adds latency without proportional
  quality gain for single-patient retrieval.
- CPU-first: the system runs on a single workstation. FastEmbed provides
  optimized CPU inference with ONNX Runtime, avoiding GPU dependencies.
- COSINE distance: clinical text similarity is about semantic meaning, not
  magnitude. COSINE is invariant to document length, which matters because
  clinical notes vary from 50 to 2000+ tokens.

────────────────────────────────────────
2. SPARSE EMBEDDING (Hybrid Search)
────────────────────────────────────────
Source: `src/ingestion/service.py:44-57`
        `src/shared/db_clients.py:53-59`

    Model:       prithivida/Splade_PP_en_v1
    Type:        SPLADE (Sparse Lexical and Expansion)
    Storage:     Qdrant named vector "text-sparse"

Why SPLADE:
- Exact term matching: clinical queries often contain specific drug names
  ("Lisinopril"), lab values ("creatinine 2.1"), or ICD codes that dense
  embeddings模糊. SPLADE guarantees exact lexical match.
- Learned expansion: SPLADE expands terms to related medical vocabulary
  (e.g., "MI" → "myocardial infarction"), providing recall that pure
  BM25 cannot achieve.
- Complementary to dense: dense captures semantic similarity ("chest pain"
  ≈ "thoracic discomfort"), SPLADE captures exact terminology. Together
  they cover both paraphrase and precision cases.
- Storage efficiency: sparse vectors are stored as (indices, values) pairs,
  not dense 768-dim arrays. For clinical notes, sparse adds ~5-15% storage
  overhead vs. the dense vector.

────────────────────────────────────────
3. CHUNKING STRATEGY
────────────────────────────────────────
Source: `src/retrieval/indexing.py:342-467` (DocumentChunker)

    chunk_size:   400 tokens
    overlap:      50 tokens
    method:       Sentence-boundary-aware sliding window
    tokenization: len(text) / 4 (approximate)

Why 400/50:
- bge-base-en-v1.5 has a 512-token max input. 400 tokens leaves 112 tokens
  of headroom for the [CLS] token and potential tokenization variance.
- 50-token overlap ensures clinical facts spanning chunk boundaries
  (e.g., "The patient was diagnosed with / community-acquired pneumonia")
  appear in at least one chunk intact.
- Sentence-boundary splitting: clinical notes are paragraph-structured.
  Splitting at sentence boundaries preserves complete clinical statements.
  Word-boundary fallback handles notes without sentence punctuation.
- Chunk ID = "{node_id}_chunk_{index}": preserves traceability to the
  parent clinical event for citation purposes.

────────────────────────────────────────
4. VECTOR SEARCH PARAMETERS
────────────────────────────────────────
Source: `src/retrieval/config.py:9-19`
        `src/retrieval/service.py:84-120`

    Dense vector name:    "text-dense"
    Sparse vector name:   "text-sparse"
    Prefetch multiplier:  2 (prefetch_k = top_k × 2)
    RRF rank constant:    k = 60
    Dense fallback:       0.60 threshold
    Collection:           "clinical_snapshots"

Why these values:
- Prefetch 2×: for top_k=10, we prefetch 20 candidates from each vector
  search, then RRF-fuse and re-rank. 2× is conservative — medical retrieval
  prioritizes recall over latency.
- RRF k=60: the standard constant from the original RRF paper (Cormack et al.
  2009). k=60 means the first-ranked document gets score 1/61 ≈ 0.0164.
  This is well-tested across domains and provides smooth rank decay.
  Clinical retrieval doesn't need custom k — the intent-based Qdrant filters
  do the heavy lifting for precision.
- Dense fallback 0.60: if sparse search fails (e.g., SPLADE model not
  loaded), we fall back to dense-only with a strict threshold. 0.60 is
  empirically tuned — below 0.50 returns too many irrelevant results for
  clinical use.

────────────────────────────────────────
5. RETRIEVAL LIMITS
────────────────────────────────────────
Source: `src/retrieval/config.py:21-23`

    default_top_k:     10
    agent_max_docs:    15

Why these limits:
- top_k=10: clinical encounters are information-dense. A single encounter
  group (e.g., "Cardiology Consultation 2024-01-15") may contain 3-5 chunks.
  10 results typically cover 2-3 relevant encounters.
- agent_max_docs=15: the ClinicalReasoner operates over retrieved documents.
  15 documents is the upper bound for LLM context — beyond this, the
  reasoning explanation becomes too long and the LLM loses focus.
- Adaptive prefetch: `_adaptive_prefetch()` scales based on estimated
  encounter count (30/60/90) to avoid missing relevant encounters in
  large patient timelines.

────────────────────────────────────────
6. INTENT-BASED QDRANT FILTERS
────────────────────────────────────────
Source: `src/retrieval/service.py:23-74` (_INTENT_FILTER_MAP)

    Intent         │ Qdrant SHOULD Conditions
    ───────────────┼──────────────────────────────────────────
    summary        │ None (all documents)
    diagnosis      │ is_diagnosis = true
    differential   │ is_diagnosis OR is_symptom OR is_allergy
                   │ OR is_medication OR event_tag = "Investigation"
    medication     │ is_medication OR is_diagnosis OR is_allergy
                   │ OR is_symptom OR is_outcome
    allergy        │ is_allergy OR is_medication OR is_diagnosis
                   │ OR is_symptom OR is_outcome
    change_track   │ is_symptom OR is_outcome OR is_diagnosis
    trend_analysis │ is_medication OR is_outcome OR is_diagnosis
    outcome        │ is_outcome OR is_diagnosis OR is_medication
    rationale      │ None (full context needed)

Why intent-based filtering:
- Clinical queries are highly specific. A "medication" query should NOT
  return imaging results or consultation notes — they add noise.
- SHOULD (OR) logic: for "differential", we want diagnosis documents
  PLUS supporting evidence (symptoms, labs, meds). ANY of these conditions
  qualifying makes a document relevant.
- MUST (AND) logic: `patient_id` is always MUST — we never cross patient
  boundaries. This is a hard clinical safety constraint.
- No filter for summary/rationale: these intents need the full clinical
  picture, so all documents for the patient are candidates.

8. LLM GENERATION PARAMETERS
────────────────────────────────────────
Source: `src/retrieval/config.py:29-35`
        `src/agent/graph/nodes.py:29-34`

    Model (local):    medgemma-1.5-4b-it-Q6_K.gguf
    Model (remote):   google/medgemma-27b-it
    Context:          16K (local) / 128K (remote)
    Temperature:
        RAG mode:     0.1  (deterministic clinical reasoning)
        Chat mode:    0.7  (natural conversation)

    Max tokens:
        RAG:          1024
        Chat:         5000

    Timeout:          60 seconds

Why these values:
- Temperature 0.1 for RAG/MCP: clinical responses must be reproducible.
  0.1 virtually eliminates sampling randomness — running the same query
  twice produces near-identical output.
- Temperature 0.7 for chat: general medical conversation benefits from
  variety. 0.7 is the standard "creative but coherent" setting.
- Max tokens 1024 for RAG: clinical summaries are concise by design.
  1024 tokens (~750 words) is sufficient for a thorough differential
  diagnosis with citations.
- Q6_K quantization: 6-bit quantization of MedGemma 4B — minimal quality
  loss (<1% perplexity increase) with 40% memory reduction, enabling
  single-GPU inference.

────────────────────────────────────────
9. CONFIDENCE THRESHOLDS
────────────────────────────────────────
Source: `src/retrieval/config.py:37-50`

    routing_fallback_threshold:    0.70
    retrieval_gatekeeper_threshold: 0.15
    generation_entropy_warning:    0.30
    Confidence weights:            0.15 / 0.25 / 0.30 / 0.30
    Labels: Low < 0.50, Medium < 0.75, High >= 0.75

Why these values:
- Routing 0.70: empirically tuned. Below 0.70, the IntentClassifier is
  uncertain about the query type. Forcing RAG (local patient data) is
  safer than sending an ambiguous query to PubMed, where irrelevant
  literature could be synthesized into a plausible-sounding wrong answer.
- Retrieval gatekeeper 0.15: after RRF normalization, scores below 0.15
  indicate the retrieved documents have weak semantic overlap with the
  query. At this level, the system flags has_insufficient_data rather
  than reasoning over poor evidence.
- Generation entropy 0.30: token-level entropy above 0.30 means the LLM
  is sampling from a flat distribution (uncertain). This triggers a
  warning but doesn't block the response — it's advisory.
- Weights (0.15/0.25/0.30/0.30): generation and validation are weighted
  highest because they directly impact the final output quality. Routing
  is weighted lowest because misclassification is partially mitigated by
  the confidence-gated fallback mechanism.

10. TEMPORAL WINDOWS
────────────────────────────────────────
Source: `src/retrieval/config.py:25-27`

    temporal_window_days:  7
    summary_window_days:  30

Why these values:
- 7-day window: for change tracking and trend analysis, the system focuses
  on recent events. A 7-day window captures acute clinical changes
  (e.g., post-surgery recovery, medication titration) without being
  overwhelmed by historical data.
- 30-day summary: for summary intent, a 30-day window provides a
  clinically meaningful snapshot — long enough to see treatment response,
  short enough to be relevant to current decision-making.

PARAMETER SELECTION METHODOLOGY
────────────────────────────────────────

1. LITERATURE-GROUNDED: RRF k=60 comes from the original paper. COSINE
   distance is standard for text similarity. bge-base-en-v1.5 is validated
   on MTEB benchmarks.

2. EMPIRICALLY TUNED: routing threshold (0.70), retrieval gatekeeper (0.15),
   and temporal windows were tuned against the 10-encounter patient timeline
   in Data/data.json using the 23-test validation suite.

3. DOMAIN-CONSTRAINED: temperature 0.1 for clinical modes, max_tokens 1024

  not optimization targets.

4. HARDWARE-CONSTRAINED: 400-token chunks, 768-dim embeddings, CPU-only
   FastEmbed — designed for single-workstation deployment without cloud
   dependencies.

Q6: How do the two MCPs (MedMCP and Visualization MCP) work?
────────────────────────────────────────

The system exposes two MCP (Model Context Protocol) services on a single
FastAPI server (port 8002). They serve different purposes: MedMCP retrieves
external medical evidence from the internet, and Visualization MCP renders
clinical charts from patient observation data.

────────────────────────────────────────

- Fallback: `_rule_based_fallback()` when Groq is unavailable — same rules
  implemented deterministically without LLM.

────────────────────────────────────────
DATA EXTRACTION FOR VISUALIZATION
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:1384-1458` (_extract_patient_data_for_viz)

The agentic graph's `generate_visualization` node extracts data from Qdrant:

    1. Scrolls all points for the patient_id
    2. For Observation resources: parses TOON content for numeric measurements
       using `extract_observation_values()`
    3. For Encounter resources: extracts phase/event data for timeline
    4. Splits into per-chart datasets:
        renal_data:    observations with "creatinine" or "egfr"
        cardiac_data:  observations with "bnp" or "lvef"
        timeline_data: encounters (or all observations as fallback)
    5. Sends each dataset to MCP /mcp/viz/render in parallel

Three charts are generated per visualization request:
    Chart 1 — Renal Function (dual_line)
    Chart 2 — Cardiac Markers (line)
    Chart 3 — Clinical Timeline (gantt)

CAPTION GENERATION
────────────────────────────────────────
Source: `src/agent/graph/nodes.py:1561-1622` (_generate_caption)

After chart rendering, an LLM-generated caption describes the clinical trend:
    - Input: up to 15 observation summaries (timestamp | event | measurements)
    - System prompt: "Write a concise 2-4 sentence clinical caption describing
      the trend over time. Focus on changes. Mention specific values."
    - Fallback: rule-based caption if LLM fails (direction + event list)
