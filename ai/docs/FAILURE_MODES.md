# AI Section — Failure Mode Tables

For each row: how the failure is detected, what the system actually does about it (not what it should do), the user-visible effect, and how it recovers. Every row is sourced from reading the actual handling code — not from a design intention. Where nothing catches a failure, that's stated as plainly as where something does.

See [`SYSTEM_OVERVIEW.md`](SYSTEM_OVERVIEW.md) for the data flow these failures occur in.

## Cross-cutting observation

Every DOC2FHIR adapter (OCR, Mapper, Downstream, HAPI FHIR, Callback) classifies errors by retryability and backs off — a real, consistent resilience pattern. The Clinical AI System's MCP call now has an equivalent on its default path — retry+backoff via `MCPToolManager` ([ADR-012](adr/012-mcp-protocol-adoption.md)) feeding into per-source circuit breakers inside MedMCP itself for PubMed/OpenFDA/MedlinePlus ([ADR-013](adr/013-per-source-circuit-breakers-medmcp.md)) — but the asymmetry isn't fully closed: the `MCP_TRANSPORT=rest` rollback path is still single-attempt catch-and-degrade by design, and Groq/RxNorm calls inside MedMCP have no circuit breaker. If either subsystem is hardened next, that's the concrete remaining gap, not a general "add more error handling" task.
