\subsection{Overview and Design Objectives}

The primary objective of developing the proposed mobile application is to
provide a secure, efficient, and patient-centered platform for managing
personal health information within the digital medical ecosystem integrated
with the FHIR-compliant backend.

\subsection{Authentication Flow \& Account Security}
Authentication in CFI-Care is delegated entirely to Keycloak, an open-source Identity and Access Management server that implements the OpenID Connect (OIDC) protocol on top of OAuth 2.0. This approach means the mobile app never handles or stores user credentials, it only deals with tokens issued by Keycloak after the user authenticates.

\subsubsection{Login and Register Flow}
The Login and Register flow uses the Authorization Code Flow with \textbf{PKCE} (Proof Key for Code Exchange), implemented via the \textbf{flutter\_appauth} package\cite{flutter_appauth}.

\subsubsection{Email Verification Code Pipeline}
During the email verification process, a unique six-digit code is generated and saved within the Keycloak authentication session. This code is then delivered to the user's email address through Keycloak's email service using a customized HTML template. The user is presented with a verification page where the received code can be entered. Upon submission, the entered code is compared with the code stored in the session. If the codes match, the user's email address is successfully verified and the registration process proceeds. Otherwise, an error message is displayed, allowing the user to request a new verification code and try again.

\subsubsection{Real-Time Image Quality Assessment via Laplacian Variance}
After any image is picked from the gallery or camera, ImageQualityService.computeBlurScore() runs automatically. The algorithm computes if the image or the scanned photo is blurry or not:
\begin{enumerate}
    \item Convert to grayscale to reduce each pixel to a single value and remove color noise that could interfere with the edge detection.
    \item Computes the variance of all Laplacian responses. A high variance means many sharp edges (a clear image). A low variance means smooth, uniform regions (a blurry image).
    \item The threshold is set at 80.0: any score below this triggers an orange warning banner in the UI: "Image looks blurry. Try retaking or enhance it."
\end{enumerate}

\subsubsection{Mathematical Magic Filter Enhancement Engine}
If the image is flagged as blurry (or the user simply wants better quality), the Magic Filter button applies a 6-step document enhancement pipeline:
\begin{table}[H]
\centering
\caption{Image Preprocessing Pipeline}
\label{tab:image_preprocessing}
\begin{tabular}{|c|p{4cm}|p{8cm}|}
\hline
\textbf{Step} & \textbf{Operation} & \textbf{Purpose} \\ \hline
1 & Grayscale & Removes color noise and reduces the processing space. \\ \hline
2 & Percentile histogram stretch (2\%--98\%) & Corrects uneven lighting while preserving image details without binarization. \\ \hline
3 & Unsharp mask (radius 1, amount 2.5) & Enhances text edges while maintaining gradient information. \\ \hline
4 & 8-connected Laplacian convolution ([-1,-1,-1,-1,9,-1,-1,-1,-1]) & Sharpens both horizontal, vertical, and diagonal text strokes. \\ \hline
5 & S-curve contrast boost (factor 1.5) & Increases contrast by pushing the paper background toward white and the ink toward black. \\ \hline
6 & Auto-invert check & If more than 50\% of pixels are dark, the image is inverted to ensure black text on a white background. \\ \hline
\end{tabular}
\end{table}
The enhanced image is saved as a new file (enhanced\_FileName) and the blur score is re-computed on the result so the warning clears if enhancement succeeded.

\subsubsection{Hardware-Accelerated Accelerometer Spirit Level}
One of the most common problems with phone-based document scanning is perspective distortion: when the phone is held at an angle over the document, the resulting image is trapezoid-shaped rather than rectangular, making text harder to read and OCR less accurate. To address this, the CFI-Care scanner includes a real-time spirit level built using the device's accelerometer.

\paragraph{Mathematical Mechanism}
The sensors\_plus \cite{sensors_plus} package provides a continuous stream of accelerometer events. The scanner subscribes to this stream in \textbf{\_initSensors()}.
\begin{itemize}
    \item The accelerometer reports gravitational force in m/s² along three axes. When the phone is held perfectly flat and parallel to a surface, both x and y approach 0 and only z carries the full gravitational value (~9.8). The threshold of 0.7 on both axes was chosen experimentally to give a comfortable tolerance — the phone does not need to be perfectly flat, just reasonably aligned.
    \item The bubble's position is a direct mapping of the accelerometer's x and y values. When the phone tilts right, the bubble moves right. When it tilts forward, it moves down, exactly like a physical spirit level. The bubble and its containing ring turn green when the phone is level and red when it is not.
\end{itemize}

Finally, the system is designed to support integration with wearable and smart health devices, such as smartwatches, to collect physiological data including heart rate and other vital signs Using Google Health\_Connect\cite{android_health_connect}. 

\subsubsection{Health Connect Local Architecture Framework}
Health Connect is a database that's stored on your device. This means that Google doesn’t use the cloud to store data that’s sent to Health Connect by connected applications.

Health Connect facilitates interoperability among Android health applications by providing a centralized platform for sharing wellness and fitness data without requiring direct integrations between applications. The platform offers APIs for both storing and retrieving medical records, while also providing users with granular control over data access permissions and a dedicated interface for viewing their medical information.

\subsubsection{Android API Version Compatibility Abstraction Layer}
\begin{itemize}
    \item \textbf{Android 14 Implementation Matrix (API Level 34):} Health Connect is baked directly inside core native OS layer environments as a native structural framework component module, eliminating setup loops. Settings $\rightarrow$ Security and Privacy $\rightarrow$ Privacy Controls $\rightarrow$ Health Connect.

\end{itemize}

\subsubsection{Granular Security Access Permissions Model}
One of the key benefits of Health Connect is its support for granular permissions. Instead of granting applications unrestricted access to all health information, users can authorize access to individual data categories. This fine-grained permission model strengthens privacy and security while allowing applications to access only the data necessary for their functionality.

\subsubsection{Clean Architecture Core Design Philosophy}
To ensure a scalable, maintainable, and testable codebase for the patient mobile application, this project adopts principles of Clean Architecture.

Clean Architecture is a layered software design paradigm that promotes clear separation of concerns, dependency management, and modularization of application logic. The fundamental goal of this approach is to isolate core business rules from implementation details and platform-specific frameworks, thereby improving long-term maintainability and facilitating unit testing \cite{clean_arch_flutter}.

According to the Flutter documentation on application architecture, well-structured applications organize code into logical layers that separate the user interface, application logic, and data handling. The documentation emphasizes the importance of isolating state management, dependency injection, and data access concerns to support growth and complexity in larger applications \cite{flutter_architecture}.

As illustrated in Figure~\ref{fig:clean-architecture}, the application is structured into three principal layers: the presentation layer, the domain layer, and the data layer. Each layer has a distinct responsibility and communicates with adjacent layers through abstract interfaces, ensuring that dependencies always point inward toward business logic rather than outward toward infrastructure or frameworks \cite{clean_arch_flutter}.

\subsubsection{Structural Layer Architecture Breakdown}
\paragraph{Presentation Layer}
This outermost layer contains code that directly interacts with the user interface. In the context of this Flutter application, it includes widgets, screens, routing logic, and Riverpod providers to manage application state when implemented. The presentation layer orchestrates the flow of data from use cases in the domain layer to the UI and captures user interactions for processing. Presentation logic is kept distinct from business rules and data access to avoid tightly coupling UI changes with core system logic \cite{clean_arch_flutter}.

\paragraph{Domain Layer}
The domain layer encapsulates the core business logic and entities of the system. It is independent of Flutter or any external dependencies. This layer defines use cases that represent application-specific operations, such as requesting document access or scheduling appointments, and serves as the central coordinator of business rules. The domain layer’s independence from external libraries and frameworks enhances testability and ensures that business logic can be validated in isolation \cite{clean_arch_flutter}.

\paragraph{Data Layer}
The data layer is responsible for integrating with external systems, including APIs, local storage, and the backend FHIR server. It provides implementations of repository interfaces defined in the domain layer and manages data transformation between network responses, local models, and domain entities. The layered separation ensures that external dependencies do not leak into the domain or presentation layers \cite{clean_arch_flutter}.

\subsubsection{Centralized Runtime Hardware Permission Handler}
To ensure a secure and seamless interaction with device hardware, the application implements a centralized asynchronous mechanism for managing runtime permissions. This approach abstracts the complexity of the \texttt{permission\_handler} library and follows established patterns for robust permission management \cite{anthony2025permissions}. The function \texttt{handlePermission} provides a unified interface for requesting access to sensitive resources such as the camera, storage, or microphone.

The function operates as a \texttt{Future<bool>}, returning a boolean value to indicate the success or failure of the authorization process. Upon invocation, the function executes the following logic flow:
\begin{enumerate}
    \item \textbf{Asynchronous Request:} It initiates a request to the underlying operating system using \texttt{permission.request()}. The execution yields until the user interacts with the system dialog or the operating system returns the current status.
    \item \textbf{Status Evaluation:} The returned \texttt{PermissionStatus} is evaluated against standard authorization states:
          \begin{itemize}
              \item \textbf{Granted:} If the user approves the request (\texttt{isGranted}), the function immediately returns \texttt{true}, allowing the calling process to proceed.
              \item \textbf{Permanently Denied:} If the permission is flagged as \texttt{isPermanentlyDenied} (a state where the operating system suppresses further prompts due to repeated denials), the system intervenes to prevent a silent failure. It displays a toast notification instructing the user to enable the permission manually and invokes \texttt{openAppSettings()} to redirect the user to the device’s settings menu.
              \item \textbf{Denied:} In cases of a standard denial, a feedback message is displayed via \texttt{Fluttertoast} to inform the user of the restriction, and the function returns \texttt{false}.
          \end{itemize}
\end{enumerate}

By encapsulating this logic, the system ensures that permission failures are handled gracefully, guiding users through recovery steps when necessary rather than causing application crashes or unresponsive features. The implementation of this logic is demonstrated in Listing \ref{lst:perm_logic}. \newpage
\begin{lstlisting}[
    language=Java, 
    basicstyle=\ttfamily\footnotesize, 
    frame=single, 
    breaklines=true, 
    caption={Asynchronous Permission Handling Function}, 
    label={lst:perm_logic}
]
import 'package:permission_handler/permission_handler.dart';
import 'package:fluttertoast/fluttertoast.dart';

Future<bool> handlePermission(
  Permission permission,
  String name,
) async {
  final status = await permission.request();

  // Case 1: Permission Granted
  if (status.isGranted) {
    return true;
  }

  // Case 2: Permanently Denied (Requires Settings)
  if (status.isPermanentlyDenied) {
    Fluttertoast.showToast(
      msg: '$name permission permanently denied. Enable it in settings.',
    );
    openAppSettings();
    return false;
  }

  // Case 3: Standard Denial
  Fluttertoast.showToast(msg: '$name permission denied');
  return false;
}
\end{lstlisting}

\subsubsection{Architectural Permission Guard Best Practices}
\begin{itemize}
    \item \textbf{Contextual Permission Requests:} To avoid overwhelming the user and to establish context, the application rejects the traditional ``up-front'' permission model (where all permissions are requested at launch). Instead, a \textit{Contextual Request} pattern is employed. Permissions are only requested at the specific moment a feature is invoked. For example, access to the \texttt{Camera} is requested solely when the user attempts to scan a medical report.
    \item \textbf{Transparent Rationale and Trust Building:} In compliance with privacy best practices, the application explains the ``Why'' before the ``How.'' Prior to triggering the system permission dialog, the application presents a custom UI explanation detailing exactly why a specific permission is needed and how it benefits the user. This transparency is critical in a healthcare context, increasing the likelihood of approval and reinforcing the patient's understanding that their data is being used strictly for medical management.\cite{daydreamsoft2025permissions}
    \item \textbf{User Agency and Graceful Degradation:} The system is designed to respect user choices without compromising the core functionality of the application. If a user denies a non-critical permission, the app enters a state of \textit{Graceful Degradation}. The application avoids repetitive prompting (``nagging''), ensuring a respectful user experience. \cite{daydreamsoft2025permissions}
    \item \textbf{Comprehensive State Lifecycle Handling:} The application logic accounts for the full lifecycle of permission states, ensuring stability across different scenarios\cite{daydreamsoft2025permissions}\cite{boudanes2024permissions}:
          \begin{itemize}
              \item \textbf{Granted:} The feature proceeds immediately.
              \item \textbf{Denied:} The feature is disabled, and the user is informed of the limitation.
              \item \textbf{Permanently Denied:} In cases where the user has selected ``Don't ask again,'' the application detects this state and provides a subtle option to guide the user to the system \texttt{App Settings} menu for manual enablement, should they choose to do so later.
          \end{itemize}
\end{itemize}

\subsection{Firebase Cloud Messaging (FCM) Push Notifications}
The system uses Firebase Cloud Messaging (FCM) to deliver real-time push notifications from the Node.js backend to the Flutter mobile app. FCM acts as a broker: the backend never sends a message directly to a device — it sends a message to Google's FCM servers, which deliver it to the target device using its unique FCM token.

\subsubsection{Transactional Notification Lifecycle Flow}
\paragraph{Token Registration Pipeline}
\begin{itemize}
    \item Before any notification can be sent, the backend must know the device's Firebase Cloud Messaging (FCM) token.
    \item On the Flutter side, the application calls FirebaseMessaging.instance.getToken() to obtain the device's unique FCM token.
    \item The token is then sent to the backend through a dedicated HTTP POST request to \texttt{/FCM/fcm-token}. Token rotation is handled automatically. Whenever Firebase generates a new token, the updated value is sent again to the same endpoint.
\end{itemize}

\paragraph{The Shared Sender Utility Broker}
All notifications go through one private function:
\begin{itemize}
    \item Before sending a notification, the backend retrieves the recipient's FCM token from Redis using the user's identifier. If no token is found, the notification is skipped because the user does not have a registered device.
    \item The backend then sends a Firebase Cloud Messaging (FCM) message containing both notification and data payloads. Notifications are sent with high priority to ensure timely delivery.
    \item Each notification message consists of two components: a Notification Payload containing user-visible string items, and a Data Payload carrying key-value schemas utilized by state engines to refresh individual context channels.
\end{itemize}

\subsubsection{Notification Event Schemes & Routing Topology}
The system defines four distinct event types, each triggering a different UI response:

\paragraph{Access Request Handshakes (\texttt{grant\_request} / \texttt{family\_request})}
When a doctor or caregiver submits a patient's OTP through the \texttt{/verify-practitioner-otp} or \texttt{/verify-caregiver-otp} endpoint, the backend first validates the OTP against Redis and retrieves the corresponding patient identifier. A pending handshake record is then created and an FCM notification is sent to the patient.

Depending on the requester type, the notification payload contains either the \texttt{grant\_request} or \texttt{family\_request} event type. Upon receiving the notification, the Flutter application refreshes the appropriate provider and displays a visual notification to the user. Doctor requests trigger an orange snackbar and refresh the pending grants list, while caregiver requests trigger a purple snackbar and refresh the pending family requests list.

\paragraph{Approval Confirmations (\texttt{grant\_approved})}
When a patient approves an access request through the \texttt{/create-grant} endpoint, the backend creates a grant record in Redis with a predefined time-to-live (TTL). The patient's display name is retrieved from the FHIR server and included in an approval notification sent to the requester.

The notification contains the event type \texttt{grant\_approved}. Upon receipt, the Flutter application refreshes the accessible members list, navigates the requester to the profile tab, and displays a green snackbar indicating that access has been approved.

\paragraph{Data Synchronization Push Streams (\texttt{data\_updated})}
Whenever a patient's health data is modified, the backend determines whether the update was performed by the patient or by a caregiver.

If a caregiver updates the patient's data, a notification is sent to the patient informing them of the change. Conversely, if the patient updates their own data, all active caregivers associated with that patient are notified. This implementation follows a fan-out notification pattern, where a single patient update may generate notifications for multiple caregivers. The Flutter application displays an informational snackbar upon receiving a \texttt{data\_updated} event.

\subsubsection{Target Group and User Segmentation}
Stakeholders are categorized into Internal Stakeholders, who are directly involved in the development and operation of the system, and External Stakeholders, who utilize the system's end products.

\subsubsection{External Stakeholders Interaction Matrix}
External stakeholders are the primary users of the system. Their interaction drives the application's core functionality.

\paragraph{Patients (Primary Users)}
\begin{itemize}
    \item \textbf{Data Management:} Patients interact with the mobile interface to upload medical documents (lab results, scans) and view their historical data presented in a structured "Major Events" timeline.
    \item \textbf{Access Control:} They possess full authority over their data privacy. Patients receive requests from doctors for data access and can grant permissions (Read-Only or Read-Write) for a specific duration. Crucially, they retain the ability to revoke this access at any time.
    \item \textbf{Family Management:} Patients can authorize family members to view their health records for monitoring purposes.
    \item \textbf{System Benefits:} Eliminates physical paperwork by consolidating history into a single mobile repository, giving patients absolute control over authorization terms, and improving continuity of care.
\end{itemize}

\paragraph{Family Members \& Caregivers (Secondary Users)}
\begin{itemize}
    \item \textbf{Monitoring:} Through shared access granted by the patient, family members can view health trends and documents to assist in care.
    \item \textbf{Administrative Support:} Unlike doctors, family members have the permission to book appointments, and change data on behalf of the patient, facilitating care for elderly or incapacitated users.
    \item \textbf{System Benefits:} Provides remote reassurance via real-time tracking, reducing logistical friction surrounding dependent clinical timelines.
\end{itemize}

\paragraph{Doctors (Service Providers)}
\begin{itemize}
    \item \textbf{Session Initiation:} While doctors primarily use the Web Interface, their actions directly trigger updates on the mobile app. A doctor initiates a "New Encounter Node" in the patient's history tree during a visit.
    \item \textbf{Access Requests:} Doctors request permission to view a patient's historical records. If granted "Write" access, they can add new diagnoses and prescriptions to the encounter node.
    \item \textbf{Scheduling Constraint Boundaries:} Doctors strictly cannot book appointments; this function is reserved for patients and their families to prevent conflict of interest or scheduling errors.
    \item \textbf{System Benefits:} Instant graph parsing accelerates diagnostic insight discovery, removing classic informational overhead when treating incoming clinical cases.
\end{itemize}
