\section{System Architecture}
\label{sec:system_architecture}

The CFI-Care system is built upon a robust three-tier architecture designed to
facilitate secure and interoperable healthcare data management. The system
integrates a modern frontend, a logic-heavy middleware layer, and a
standards-compliant backend to ensure data consistency and security. The
architecture adheres to the FHIR (Fast Healthcare Interoperability Resources)
standard for all medical data exchange and utilizes OAuth 2.0 via Keycloak for
identity management.

\subsection{High-Level Architecture}

The application operates through a strict separation of concerns. The
Presentation Layer is an Angular-based Single Page Application (SPA) that
serves as the user interface. It does not communicate directly with the data
stores. Instead, all client requests are intercepted by an Nginx Reverse Proxy,
which handles SSL/TLS termination and routes traffic to the appropriate
internal services.

The core of the backend processing is handled by the Node.js Application
Server. This server acts as the primary API gateway, implementing business
logic, enforcing security policies, and managing user sessions. It communicates
with the HAPI FHIR Server, a specialized Java-based component responsible for
persisting clinical data in compliance with the FHIR R5 standard. Data storage
is consolidated in PostgreSQL databases, while high-speed data access and
session management are handled by Redis instances.

\subsection{Node.js Application Server}

The Node.js server, built with the Express.js framework, serves as the
middleware layer that bridges the gap between the user interface and the
standardized medical records. It is designed with a modular layered
architecture to ensure scalability and maintainability.

\subsubsection{Middleware and Security}
Upon receiving a request, the server passes it through a comprehensive
middleware stack. Security headers are applied using Helmet to prevent common
web vulnerabilities. Cross-Origin Resource Sharing (CORS) is configured to
restrict access to authorized domains. Crucially, the server implements rate
limiting to protect API endpoints from abuse and utilizes a Redis-backed
session store to manage user authentication states efficiently.

\subsubsection{Routing and Services}
The application is divided into specific route modules corresponding to
healthcare domains. Dedicated endpoints manage Patients, Practitioners,
Encounters, and Episodes of Care. A specialized "History Graph" module handles
the retrieval and processing of graph visualization data.

Beneath the routing layer lies the service layer, which contains the core
business logic. These services act as proxies to the FHIR server, transforming
raw FHIR JSON into formats optimized for the frontend, such as the D3.js
visualizations. They also handle document processing tasks, such as converting
base64 strings to PDF files for binary storage.

\subsection{Data Persistence and Schema}

The system utilizes a polyglot persistence strategy, employing different
database technologies for specific use cases to maximize performance.

\subsubsection{Relational Data}
The primary storage engine is PostgreSQL. It is divided into two logical
segments. The first segment supports the HAPI FHIR server, storing all standard
clinical resources (like Patients and Observations) in a highly structured
format managed by Hibernate. The second segment supports the Keycloak identity
provider, storing user credentials and realm configurations.

\subsubsection{Custom Graph Schema}
To support the unique "Medical History Graph" feature, a custom schema was
designed alongside the standard FHIR tables. This schema consists of
\texttt{encounter\_nodes} and \texttt{node\_relations}. These tables allow the
system to map standard FHIR Encounters into a Directed Acyclic Graph (DAG),
enabling the visualization of a patient's journey through time with causal
links between medical events.

\subsubsection{Caching and Auditing}
Redis is utilized for ephemeral data storage. One instance is dedicated to
storing user sessions, ensuring fast authentication checks. A second Redis
instance operates in Append-Only File (AOF) mode to store audit logs, providing
a persistent and high-speed trail of system activities.

\subsection{Request/Response Flow and Data Transformation Pipeline}
\label{subsec:request_response_flow}

Understanding how requests traverse the CFI-Care system is essential for
comprehending the architecture's design decisions. A typical request from the
frontend follows a well-defined path through multiple layers, each contributing
specific functionality: authentication verification, input validation, business
logic execution, data transformation, and response formatting.

\subsubsection{Request Ingress and Authentication}
A request originates from the Angular frontend as an HTTP request, typically
including a Bearer token in the Authorization header. The request first reaches
the Nginx reverse proxy, which acts as the external-facing gateway. Nginx
terminates the TLS/SSL connection, decrypts the HTTPS payload, and forwards the
unencrypted request to the Node.js server over the private Docker network.
Before the request reaches application logic, it passes through the Helmet
middleware, which applies security headers to prevent common web
vulnerabilities such as XSS (Cross-Site Scripting), CSRF (Cross-Site Request
Forgery), and clickjacking. The CORS middleware then validates that the request
originates from an authorized frontend domain; requests from unauthorized
origins are rejected immediately.

The next critical middleware validates the JWT token embedded in the
Authorization header. The Node.js server maintains a cached set of public keys
(JWKS) from Keycloak, updated periodically to handle key rotations. The token
is cryptographically verified against these keys. If verification succeeds, the
token claims (user ID, roles, permissions) are extracted and attached to the
request context. If verification fails---due to an invalid signature, expired
token, or missing token---the middleware returns a 401 Unauthorized response,
and the request is rejected before reaching downstream services.

\subsubsection{Concrete Example: Patient Data Retrieval}
Consider a clinician's request to retrieve a patient's full medical history.
The frontend issues a GET request to \texttt{/api/patients/:patientId}. After
passing authentication and security middleware, the request reaches the routing
layer, which dispatches it to the PatientService controller. The controller
immediately implements input validation: the patientId parameter is checked to
ensure it conforms to expected format (numeric ID or UUID, depending on the
system design), and the authenticated user's roles are verified to confirm they
have permission to access that patient's data (enforcing HIPAA privacy
principles).

Before querying the database, the controller checks the Tier 1 cache (managed
by cacheHelper). The middleware generates a deterministic cache key from the
request URL: \texttt{cache:patients:patientId:\{id\}}. If a valid cache entry
exists, the cached patient data is immediately returned with a 200 OK response,
bypassing all downstream processing. This cache hit path typically completes in
20-50 milliseconds.

If a cache miss occurs, the request proceeds to the PatientService layer. The
service constructs a FHIR query and forwards it to the HAPI FHIR server via an
HTTP call: \texttt{GET /fhir/Patient/\{patientId\}}. The FHIR server retrieves
the patient resource from PostgreSQL, performs any necessary transformations or
computations required by the FHIR R5 standard, and returns the response in FHIR
JSON format.

The PatientService receives the FHIR response and performs transformation
operations: extracting relevant fields, formatting dates to match frontend
expectations, computing derived values (e.g., age from birthdate), and
sanitizing sensitive information if necessary. The transformed data is then
stored in the Redis cache with a 1-hour TTL for future requests. Finally, the
response is serialized to JSON and returned to the frontend with a 200 OK
status code and appropriate cache headers to guide browser-side caching.

\subsubsection{Concrete Example: Encounter Creation and Graph Update}
The encounter creation flow demonstrates more complex interactions across
multiple system layers. When a clinician records a new consultation, the
frontend issues a POST request to \texttt{/api/encounters} with a JSON payload
containing encounter details (patient ID, encounter type, date, notes, etc.).

The request undergoes the same initial security and authentication pipeline as
before. Upon reaching the EncounterService controller, the request enters the
input validation phase. The encounter data is validated against a schema
ensuring that all required fields are present and correctly formatted. The
encounter date is verified to be a valid date and logically consistent (e.g.,
encounter date cannot be in the future). The patient ID is validated to ensure
the patient exists in the system.

Next, the EncounterService constructs a FHIR Encounter resource conforming to
the FHIR R5 standard and submits a POST request to the HAPI FHIR server:
\texttt{POST /fhir/Encounter}. The FHIR server validates the resource,
generates a unique FHIR resource ID, persists the resource to PostgreSQL, and
returns the created resource with its new ID.

The encounter creation triggers a cascade of downstream operations. The
EncounterService receives the FHIR response and extracts the newly created
encounter's ID. It then invokes the historyGraphService, passing the new
encounter data. The historyGraphService performs a temporal scan of existing
nodes for the patient, identifies potential parent nodes based on clinical
rules and temporal windows, and creates appropriate edges in the
node\_relations table. This graph construction may take several hundred
milliseconds to several seconds depending on the patient's history size.

Concurrently, multiple cache entries are invalidated. The patient-specific Tier
2 graph cache is cleared immediately, ensuring that the next graph
visualization request triggers a fresh reconstruction. The Tier 1 cache entry
for the \texttt{/api/patients/\{patientId\}} endpoint is also invalidated,
forcing a fresh FHIR server query for updated patient data.

Finally, the EncounterService returns the newly created encounter resource to
the frontend with a 201 Created status code. The response includes the
encounter's FHIR ID, allowing the frontend to reference this specific encounter
in subsequent requests.

\subsubsection{Validation Points and Error Conditions}
Throughout this flow, validation occurs at multiple critical junctures. Input
validation at the controller layer ensures that user-supplied data conforms to
expected types and ranges. Business logic validation in the service layer
verifies that operations are consistent with clinical rules (e.g., an encounter
date cannot precede a patient's birth date). FHIR resource validation at the
HAPI FHIR server ensures that resources conform to the FHIR R5 specification,
preventing invalid data from being persisted.

Error conditions at any stage result in appropriate HTTP status codes and error
messages: 400 Bad Request for input validation failures, 403 Forbidden for
authorization violations, 404 Not Found for missing resources, 409 Conflict for
data consistency violations, and 500 Internal Server Error for unexpected
server failures. Each error response includes a structured JSON object with a
unique error code, human-readable message, and optionally, detailed information
about the nature of the failure, enabling clinicians and developers to
understand and address issues.

\subsection{Error Handling and Fault Tolerance}
\label{subsec:error_handling}

The CFI-Care architecture recognizes that healthcare systems cannot tolerate
downtime or data loss. Error handling and fault tolerance are designed into
every layer to ensure reliable operation and graceful degradation under failure
conditions.

\subsubsection{Layered Error Handling Strategy}
Errors propagate through the CFI-Care system in a controlled, layered manner.
At the lowest layer, database operations (PostgreSQL queries, Redis operations)
can fail due to connection timeouts, query errors, or resource unavailability.
The Node.js middleware layer implements error handlers that catch these
exceptions, log them for diagnostics, and transform them into appropriate HTTP
error responses that safely communicate the failure to clients without exposing
internal implementation details (such as database error messages or stack
traces).

The service layer implements domain-specific error handling. When a FHIR server
call fails, the service layer attempts to determine whether the failure is
transient (temporary network issue) or persistent (FHIR server down, resource
not found). For transient failures, the service implements exponential backoff
retry logic: the first retry occurs after 100 milliseconds, the second after
200 milliseconds, and subsequent retries double the wait time, capped at a
maximum of 30 seconds. This approach allows temporary outages to resolve while
avoiding overwhelming a recovering server with immediate retry attempts. For
persistent failures, errors are returned to the client immediately rather than
consuming retry attempts.

The controller layer handles errors from services and formats them
appropriately for the client. A service that cannot retrieve a patient record
returns an error code; the controller translates this into a 404 Not Found HTTP
response with descriptive messaging.

\subsubsection{Fallback Mechanisms and Graceful Degradation}
When the FHIR server becomes temporarily unavailable, the CFI-Care system
implements fallback strategies to maintain partial functionality. The caching
layer becomes the primary data source: clinicians can still access patient
records that were recently viewed, as these records remain in the Redis cache.
While cached data may not reflect the absolute latest updates, it permits
continued operation during brief FHIR server outages.

For the Patient History Graph, if the graph reconstruction fails due to FHIR
server unavailability, the system returns a cached version of the graph if one
exists, even if it is slightly stale. This allows clinicians to view previously
computed graphs rather than receiving a complete failure. A notification is
displayed to indicate that the graph may not reflect recent changes.

For new operations that require FHIR server access (creating encounters, adding
diagnoses), if the FHIR server is unavailable, the system cannot proceed and
returns a 503 Service Unavailable response, informing the clinician that the
action cannot be completed at this moment. Rather than accepting incomplete or
invalid data, the system fails safely, requiring the user to retry when the
service recovers.

\subsubsection{Resilience for Cache Operations}
Redis provides the caching infrastructure for both session management and data
caching. If Redis becomes unavailable, the system implements fallback
strategies. For session caching, a secondary in-memory session store provides a
fallback mechanism, allowing authentication to continue for users with active
sessions, though new sessions cannot be created. For data caching, cache misses
gracefully trigger direct queries to the FHIR server, bypassing the cache
entirely but maintaining functionality.

Both Redis instances (session store and audit log store) are configured with
persistence mechanisms. The session Redis instance uses RDB snapshots to
periodically save state to disk, enabling recovery of active sessions if the
instance restarts. The audit log Redis instance operates in AOF (Append-Only
File) mode, ensuring every write is persisted to disk before acknowledging the
write, guaranteeing that audit logs are never lost even if the Redis instance
crashes.

\subsubsection{Logging and Observability for Error Diagnosis}
All errors are logged with structured logging that includes timestamp, error
level (ERROR, WARN, INFO), service component generating the error, error code
and message, request context (user ID, patient ID, operation being performed),
and stack trace for unexpected exceptions. This structured logging enables
rapid diagnosis of issues: operators can search logs by error code to identify
all instances of a particular failure, by user ID to understand a user's
experience during an outage, or by component to focus on specific services.

Critical errors are propagated to alerting systems, enabling operators to be
notified of failures in real-time. For instance, if the FHIR server becomes
unavailable, an alert is triggered within seconds. If error rates exceed
thresholds, alerts notify operators that the system is degrading. This
proactive monitoring enables rapid response to emerging issues before they
impact clinicians' ability to deliver care.

\subsection{Security and Infrastructure Layer}

The infrastructure is secured through a centralized Identity and Access
Management (IAM) system using Keycloak. Keycloak handles all OAuth 2.0 and
OpenID Connect flows, issuing JSON Web Tokens (JWT) that the Node.js backend
validates against a public key set (JWKS).

All components are containerized using Docker and orchestrated via Docker
Compose. The environment is isolated within a private bridge network, with
Nginx acting as the sole entry point. Nginx enforces SSL/TLS encryption using
locally generated certificates, ensuring that all data in transit is encrypted.
Containers are configured with read-only file system mounts and strict
privilege limitations to minimize the security attack surface.
