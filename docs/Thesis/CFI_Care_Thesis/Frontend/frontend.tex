\section{Frontend}\label{chap:Frontend}

% -----------------------------------------------------------
\subsection{Overview and Design Objectives}
% -----------------------------------------------------------

The frontend of \textit{CFI-Care} was designed as an interactive medical
information system aimed at enabling healthcare professionals to efficiently
explore, manage, and reason about patient data. The primary objective was to
transform fragmented medical records into a coherent, visual, and navigable
representation of a patient's medical journey, while maintaining clinical
clarity, responsiveness, and usability across the full scope of the
application.

The frontend follows a component-based architecture implemented using the
Angular framework. Advanced data visualisation is achieved through the
integration of D3.js and Treeviz, while Bootstrap and Bootstrap Icons provide
responsive layout, visual consistency, and accessibility across devices.

The main design goals of the frontend include:
\begin{itemize}
    \item Clear separation of concerns between navigation, visualisation, and
          data manipulation.
    \item Visual prioritisation of clinically critical events through
          deliberate colour coding and animated indicators.
    \item Support for both categorical and temporal reasoning over patient
          medical data through two complementary visualisation modes.
    \item A patient-access grant workflow that balances security requirements
          with a smooth, low-friction clinical experience.
    \item A fully integrated AI-assisted chat interface that enables
          real-time clinical reasoning alongside patient data.
\end{itemize}

Component-based frontend architectures have been shown to improve scalability,
maintainability, and development efficiency in large-scale systems
\cite{componentFrontEnd2021}.

\subsection{System Architecture}
\label{sec:system-architecture}
% -----------------------------------------------------------

The CFI-Care frontend is structured as a modular, component-based single-page
application (SPA) built with Angular. The system follows a layered frontend
architecture that cleanly separates presentation, state management, domain
models, and visualisation logic.

At a high level, the architecture consists of the following layers:

\begin{itemize}
    \item \textbf{Application Shell}: Responsible for route registration,
          authentication guards, and top-level layout composition.
    \item \textbf{Feature Modules}: Self-contained UI modules grouped by
          clinical concern, covering the patient dashboard, doctor profile and
          schedule management, grant management screens, and the AI chat
          interface.
    \item \textbf{MedGraph Visualisation Module}: A dedicated
          visualisation boundary hosting both the categorical tree and the
          chronological timeline, isolated from Angular's change-detection loop
          via an iframe boundary to prevent rendering interference.
    \item \textbf{Shared Domain Models and Services}: Centralised TypeScript
          interfaces and injectable Angular services that carry application
          state and mediate all HTTP communication with the backend.
    \item \textbf{Graph Rendering Engine}: A self-contained HTML file
          (loaded inside an iframe) that combines Treeviz, D3.js, and
          vanilla JavaScript to render interactive patient journey graphs,
          communicating with the Angular host via the \texttt{postMessage} API.
\end{itemize}

\subsubsection{Route Structure and Navigation Guards}

The application defines the following client-side routes:

    \centering

    \label{tab:routes}
    \begin{tabular}{|l|l|l|}
        \hline
        \textbf{Path}           & \textbf{Component}          & \textbf{Guard}   \\
        \hline
        \texttt{/}              & Redirect to \texttt{/dashboard} & ---             \\

        \texttt{/doctor-profile}& DoctorProfileComponent      & \texttt{authGuard} \\

        \texttt{/error/:status} & GatewayErrorComponent       & ---              \\
        \hline
    \end{tabular}
\end{table}

All clinically sensitive routes are protected by \texttt{authGuard}, an
Angular route guard that verifies session validity before permitting
navigation. Unauthenticated users are redirected to the login flow. The
\texttt{/error/:status} route accepts a dynamic HTTP status code and renders a
contextual error page, handling backend or gateway failures gracefully without
exposing raw error traces to the user.

The \texttt{/med-graph/:id} route accepts a patient identifier as a path
parameter and an optional \texttt{eocId} query parameter, enabling direct
deep-linking to a specific episode of care's visualisation.

\subsubsection{Component Hierarchy}

Figure~\ref{fig:component-diag} illustrates the full component tree. The
\texttt{Dashboard} component acts as a layout compositor, combining three
child components: \texttt{TopBar} (global navigation and account controls),
\texttt{UsersPanel} (patient search, filter, and list), and \texttt{UserInfo}
(detailed clinical summary for the selected patient). The \texttt{MedGraph}
component operates independently, receiving its patient context from route
parameters and communicating with the embedded iframe via \texttt{postMessage}.

\subsection{Styling and UX Philosophy}
\label{subsec:styling}
% -----------------------------------------------------------

The CFI-Care frontend adopts a \textit{High-Contrast Clinical Design System},
intentionally crafted to balance institutional medical trust with modern,
interactive sophistication. This design approach prioritises clarity,
confidence, and rapid information recognition, all critical requirements in
high-stakes clinical environments.

\subsubsection{Colour Theory and Semantic Encoding}

The visual palette is dominated by blue-scale tones combined with cyan and
teal gradients. Deep blue hues are widely associated with trust, security, and
professionalism in healthcare interfaces, while cyan gradients introduce a
contemporary, technology-forward aesthetic suited to an AI-augmented system.

Colour is used not merely as decoration but as a primary semantic layer.
Medical event categories such as laboratory results, consultations, imaging
studies, AI-generated suggestions, prescriptions, and allergies are
consistently colour-coded across every view of the system. This allows
clinicians to identify event types instantly through pre-attentive visual
processing, without requiring explicit text reading, a principle well-supported
in visualisation research \cite{hospitalDashboards2022,interactiveDashboards2020}.

The same colour assignments are maintained across the categorical tree, the
chronological timeline, node detail panels, and the legend, ensuring that the
visual vocabulary is learned once and remains coherent throughout the
application.

\subsubsection{Visual Hierarchy and Layout Strategy}

The interface relies on a card-based information architecture layered over a
neutral background. Glassmorphism and soft elevation effects are applied
selectively to authentication cards and dashboard panels, creating visual depth
without introducing clutter.

A master-detail layout is employed throughout the patient dashboard, with a
persistent high-contrast sidebar acting as a stable navigational anchor. This
structure reduces spatial disorientation and supports rapid context switching,
which is essential in time-constrained clinical workflows
\cite{patientSafetyDashboards2021}.

\subsubsection{Typography, Iconography, and Micro-Interactions}

The Inter typeface is used consistently throughout the application to maximise
legibility across varying screen sizes and lighting conditions. Minimalist
line-based Bootstrap Icons provide language-independent visual cues,
accelerating recognition and navigation.

Within the Patient Journey Dashboard, medical events are represented as
stylised circular nodes. High-priority nodes carry red rings rendered through
CSS, drawing clinical attention without requiring user interaction. Hover
states on node circles include a smooth scale transform and an enhanced
drop-shadow filter, reinforcing the interactive affordance of each element.

The application additionally provides a dark mode, toggled via a persistent
button in the top-right corner of the graph view. The user's preference is
persisted to \texttt{localStorage}, ensuring continuity across sessions.
Dark mode applies a comprehensive set of CSS variable overrides across all
panels, the SVG canvas, modal dialogs, and sidebar components.

\subsection{Patients Dashboard}
% -----------------------------------------------------------

\subsubsection{Overview}

The Patients Dashboard, shown in Figure~\ref{fig:patients_dashboard},
functions as the primary data management hub of the system. It enables
clinicians to search, select, and review patient profiles, manage episodes of
care, and navigate to the patient journey visualisation. The dashboard is
composed of three Angular components that operate in concert: \texttt{UsersPanel},
\texttt{Users}, and \texttt{UserInfo}.

    \centering
    \includegraphics[width=0.95\linewidth]{Frontend/Images/patients_dashboard.jpeg}
    \caption{Patients Dashboard showing the master-detail layout. The left
    sidebar presents the patient navigator with search, filter, and episode
    management controls. The main panel displays the full clinical summary for
    the selected patient, including active conditions, medications, recent
    laboratory results, procedures, and a scoped encounter history.}
    \label{fig:patients_dashboard}
\end{figure}

\subsubsection{Master-Detail Layout}

The dashboard follows a master-detail layout, a design pattern widely adopted
in medical information systems \cite{patientSafetyDashboards2021}. The layout
consists of:

\begin{itemize}
    \item \textbf{Patient Navigator (Left Sidebar):} Rendered by
          \texttt{UsersPanel}, this panel contains a search bar, a filter
          panel, an ``Add Patient'' action, and a scrollable list of patient
          cards rendered by the \texttt{Users} component.
    \item \textbf{Clinical Summary View (Main Panel):} Rendered by
          \texttt{UserInfo}, this panel displays structured patient information
          in a card-based layout, updating reactively when a new patient is
          selected.
\end{itemize}

\subsubsection{Patient Navigator: Search, Filter, and Selection}

The \texttt{UsersPanel} component implements a reactive search mechanism that
filters the patient list in real time as the clinician types. A filter panel
toggles open to expose additional controls for sorting (by name, age, ID, or
last-updated timestamp) and filtering by age range. The \texttt{applyFilter}
method recombines all active criteria into a single filtered list, and the
filter panel closes automatically upon application. A reset action restores
all defaults without requiring manual field clearing.

Each patient card in the \texttt{Users} component displays the patient's name,
age, and last-updated timestamp. A colour-coded status dot provides an
immediate freshness indicator: green indicates the record was updated within
the past 30 days, and yellow indicates a stale record. This status is computed
by the \texttt{getStatus} method using a precise day-difference calculation,
providing a passive clinical alert without requiring explicit user interrogation
of individual records.

Patient selection is mediated entirely through the \texttt{SelectedPatientService},
an injectable Angular service that exposes a reactive \texttt{selectedPatientId\$}
observable. Both the \texttt{Users} component (which sets the selected ID on
click) and the \texttt{UserInfo} component (which subscribes to trigger a detail
load) communicate through this shared service without any direct parent-to-child
binding, exemplifying a clean observable-based state management pattern
\cite{angularDocs}.

\subsubsection{Patient Access Grant Workflow (OTP Handshake)}

A key usability and security feature of the patient navigator is the patient
access grant workflow, accessible via the ``Add Patient'' button at the top of
the navigator. This workflow allows a clinician to request access to a patient's
data through a time-limited, patient-initiated one-time password (OTP). The
six-digit OTP input modal is shown in Figure~\ref{fig:otp_input}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.75\linewidth]{Frontend/Images/otp_input.jpeg}
    \caption{Patient access grant modal presenting the six-cell OTP input
    field. The clinician enters the code generated on the patient's device to
    initiate the access request handshake.}
    \label{fig:otp_input}
\end{figure}

The process operates as follows:
\begin{enumerate}
    \item The patient generates a six-digit OTP on their own device.
    \item The clinician clicks ``Add Patient'' and a modal dialog opens
          presenting a six-cell OTP input field (powered by \texttt{ng-otp-input})
          with confirm and cancel actions.
    \item Upon submission, the frontend calls \texttt{handshake.verifyOtp()}
          and transitions to a ``forwarded'' state, displaying a confirmation
          that the request has been sent for the patient's approval.
    \item The component begins polling the backend via
          \texttt{handshake.pollStatus()} on a three-second interval,
          implemented using the RxJS \texttt{interval} and \texttt{switchMap}
          operators with \texttt{takeWhile} to automatically terminate polling
          when a terminal state is reached.
    \item On patient approval, the modal transitions to a ``success'' state,
          the polling subscription is cleaned up, and the patient list
          refreshes to include the newly granted patient.
    \item If the OTP is invalid, expired, or not found, distinct error states
          are rendered inline within the modal with specific, actionable
          messages.
\end{enumerate}

This design keeps the entire workflow within a single modal without page
reloads, minimising disruption to the clinician's working context.

\subsubsection{Clinical Summary View}

The \texttt{UserInfo} component loads full patient details via a \texttt{forkJoin}
of seven concurrent FHIR API calls, covering patient demographics, conditions,
encounters, medications, procedures, document references, and episodes of care,
ensuring that all data is fetched in parallel and the UI transitions to a
loaded state only once all requests complete. The component maps raw FHIR
resources to structured domain transfer objects using a set of dedicated
transformation functions (\texttt{fhirPatientToDetailsDTO},
\texttt{fhirEOCToEpisode}, \texttt{extractConditionDisplay}, etc.), isolating
FHIR-specific parsing logic from presentation concerns.

The clinical summary view organises data into clearly defined sections:
\begin{itemize}
    \item Demographics: name, age, gender, and patient identifier.
    \item Primary diagnosis, active conditions with coloured pill badges,
          and current medications.
    \item Recent laboratory results with direct PDF viewing via inline
          \texttt{DocumentReference} binary resolution.
    \item Recent procedures.
    \item A full encounter history scoped to the selected episode, with each
          encounter typed and styled according to a comprehensive encounter
          type map spanning twelve clinical categories.
\end{itemize}

\subsubsection{Episode of Care Management}

The clinical summary panel includes an episode-of-care selector allowing the
clinician to switch between multiple episodes for the same patient. The episode
selector presents a dropdown of existing episodes, and each episode selection
triggers a fresh encounter-scoped filter of conditions, medications, and
procedures, ensuring that all displayed clinical data corresponds precisely to
the chosen episode context.

New episodes can be created inline via a name input and a ``+ Add Episode''
button, which calls the FHIR EpisodeOfCare creation endpoint and immediately
appends the result to the episode list. Fallback logic handles cases where FHIR
filtering returns no data for a given episode, deriving medications from
Medication-type encounters and diagnosing from AI-Diagnosis-type encounters as
a secondary inference mechanism.

\subsubsection{Patient-Scoped MedGraph Access}

Rather than exposing the journey visualisation globally, access to the MedGraph
is embedded within the patient details card. A prominent ``Open History Graph''
button navigates to \texttt{/med-graph/:id}, passing the currently selected
episode's ID as an \texttt{eocId} query parameter. This design ensures that
any transition to the MedGraph view is explicitly scoped to the selected patient
and episode, preventing context errors and reinforcing the principle that
advanced visualisation actions should be clearly associated with their target
data objects.

\subsection{Patient Journey Dashboard}
% -----------------------------------------------------------

While traditional medical dashboards present patient data as isolated records,
clinical decision-making often requires understanding how events evolve, relate,
and unfold over time. To address this limitation, CFI-Care introduces the
\textit{Patient Journey Dashboard}, a dedicated interactive environment that
provides a holistic, visual view of a patient's complete medical history.

The Patient Journey Dashboard enables clinicians to:
\begin{itemize}
    \item Explore relationships between medical events through a hierarchical
          tree structure.
    \item Understand disease progression from initial presentation through to
          treatment and follow-up.
    \item Analyse alternative diagnostic or treatment pathways via independent
          branches.
    \item Identify clinically critical events at a glance without losing
          contextual awareness.
    \item Add, edit, and delete medical events in-place with full
          bidirectional backend synchronisation.
\end{itemize}

Rather than enforcing a single representation, the dashboard provides two
complementary visualisation modes: \textit{Categorical} and
\textit{Chronological}. Each mode offers a distinct analytical perspective over
the same underlying patient data, allowing clinicians to switch between
structural and temporal reasoning as needed.

\subsubsection{Iframe Isolation Architecture}

The graph engine is implemented as a self-contained HTML document loaded inside
an iframe within the Angular \texttt{MedGraph} component. This isolation is a
deliberate and well-reasoned architectural choice driven by three compounding
concerns. First, D3.js and Treeviz both perform direct, synchronous DOM
mutations at high frequency during zoom, pan, and re-render cycles. Angular's
Zone.js patches every asynchronous operation and triggers change detection on
each one, so running D3 inside the Angular component tree would cause hundreds
of unnecessary change-detection cycles per second during graph interaction,
degrading performance meaningfully. Second, the iframe provides a complete DOM
isolation boundary: the graph's global event listeners, CSS rules, and
third-party library globals (D3 registers several of these) cannot leak into
or conflict with the Angular host application. This goes beyond what
\texttt{NgZone.runOutsideAngular()} would achieve, which suppresses Angular's
change detection but still shares the same DOM, the same global CSS cascade,
and the same JavaScript namespace. Third, full DOM isolation enables the
visualisation layer to be developed, tested, and replaced independently,
without destabilising the broader Angular application during iteration.

Communication between the Angular host and the iframe is implemented entirely
via the \texttt{window.postMessage} API. The Angular host sends an
\texttt{INIT\_GRAPH} message on iframe load, carrying the full node list,
patient ID, and episode of care ID. The iframe dispatches
\texttt{NODE\_UPDATE} messages for every add, edit, and delete operation,
which the Angular host intercepts and forwards to the corresponding backend
API calls. Backend responses are relayed back to the iframe as
\texttt{NODE\_SAVED} or \texttt{NODE\_ERROR} messages, enabling optimistic
UI updates with rollback on failure. Figure~\ref{fig:medgraph-seq} illustrates
this message-passing sequence in full, and Figure~\ref{fig:dataflow-diag}
illustrates the complete data flow from user interaction through to backend
persistence and rollback.

\subsubsection{Node Data Model}

Each node in the patient journey graph carries the following fields:
\begin{itemize}
    \item \textbf{id}: Unique identifier (temporary client-side ID prefixed
          \texttt{temp-} until the backend assigns a persistent UUID).
    \item \textbf{text\_1}: Display title of the medical event.
    \item \textbf{father}: Parent node ID (\texttt{null} for the root node).
    \item \textbf{category}: One of nine clinical categories, each mapped to
          a distinct colour.
    \item \textbf{priority}: Low, Medium, or High.
    \item \textbf{normality}: Normal, Abnormal, or Pending.
    \item \textbf{dateIssued}: ISO date string.
    \item \textbf{details}: Free-text clinical notes.
    \item \textbf{isDiagnosis / isManualBranch}: Flags marking branch-starter
          nodes in the chronological view.
    \item \textbf{branchState}: In-progress, discontinued, or completed,
          governing branch rendering and interaction permissions.
\end{itemize}

\subsubsection{Global Controls and Interaction Modes}

The graph header provides a consistent set of controls applicable to both
views:
\begin{itemize}
    \item \textbf{Add Node}: Activates a crosshair cursor and highlights all
          selectable nodes with a green ring. Clicking any node opens a modal
          form to specify the child event's title, date, category, priority,
          normality, and details. The new node is added optimistically to the
          data array and rendered immediately; the backend is notified
          asynchronously and the temporary ID is replaced with the real UUID
          upon confirmation.
    \item \textbf{Delete Node}: Activates a ``not-allowed'' cursor and highlights
          deletable nodes with a red ring. Selecting a node triggers a
          confirmation dialog and recursively removes the target node and all
          its descendants. If the backend delete fails, all removed nodes are
          restored from a \texttt{pendingDeletes} map.
    \item \textbf{Filters}: Toggles a filter panel allowing refinement by
          category, priority, normality, and date range. Filtering is applied
          reactively to both views with parent-node inclusion logic ensuring
          that matching nodes are never orphaned from the tree.
    \item \textbf{View Toggle}: Switches between Categorical and Chronological
          modes without page reload, preserving all filter and expansion state.
\end{itemize}

Guard logic prevents modifications within discontinued branches, completed
branches, or a finished case, surfacing contextual toast messages that explain
the restriction and describe how to lift it.

\subsection{Patient Journey Dashboard — Categorical View}
% -----------------------------------------------------------

\subsubsection{Purpose and Conceptual Model}

The categorical view presents the patient journey as a hierarchical,
relationship-oriented structure. Its primary purpose is to visualise
\textbf{clinical relationships, causality, and dependency} between medical
events. In this mode clinicians can clearly observe how diagnostic steps lead
to subsequent decisions, which medical events are logically connected, and
complete clinical paths from disease onset to treatment.

\subsubsection{Hierarchical Graph Representation}

Medical events are rendered as nodes within a directed node-link graph, laid
out left-to-right using the Treeviz library. A single root node represents
the patient case origin, from which first-level category branches emerge.
When more than one root node exists in the data, for example when a patient
has multiple concurrent care pathways, the system automatically inserts a
hidden virtual root node to produce a single connected tree, ensuring Treeviz
always receives a valid hierarchy without requiring manual data normalisation.

\subsubsection{Expand and Collapse Semantics}

First-level nodes directly connected to the root carry a small expand/collapse
trigger button rendered in the top-right corner of their dot. Clicking this
button expands or collapses the entire sub-tree rooted at that node, including
all deeper descendants via the recursive \texttt{addAllDescendants} and
\texttt{removeAllDescendants} functions. To contain visual complexity, a
maximum of two first-level branches may be expanded simultaneously;
activating a third branch automatically collapses the oldest expanded branch.
This constraint preserves a coherent visual field without preventing access
to any part of the tree.

\subsubsection{High-Priority Propagation Mechanism}

Clinically critical events are visually marked with an animated pulsing red
ring rendered via a CSS \texttt{@keyframes pulse} animation. When a
high-priority node exists within a collapsed branch, the priority indicator
propagates upward to the corresponding first-level parent node. This ensures
that urgent information is never visually hidden from a collapsed state. Upon
expansion, the indicator is removed from the parent and appears solely on the
originating node, preserving both visibility and clinical accuracy
\cite{hospitalDashboards2022}.

\subsubsection{Node Relationship Indicators}

Each non-root node carries a coloured sibling badge indicating whether it is
the sole child of its parent (``SINGLE'', rendered in green) or one of
multiple siblings (``SIBLING'', rendered in blue). These indicators allow
clinicians to infer structural branching without expanding the full hierarchy,
supporting rapid structural scanning.

\subsubsection{Node Detail Sidebar}

Clicking any node opens a slide-in detail sidebar on the right of the canvas,
displaying the node's title, normality status tag, priority tag, date, category
with colour swatch, and full clinical detail text. The sidebar includes an
``Edit Node'' button that opens a draggable, resizable floating form prepopulated
with the node's current values. All edit operations are subject to the same
branch-state guard logic as add and delete operations. The form itself is
draggable via a \texttt{mousedown}-based drag handler and resizable via CSS
\texttt{resize: both}, giving clinicians flexible screen real estate management
during data entry.

\subsection{Patient Journey Dashboard — Chronological View}
% -----------------------------------------------------------

\subsubsection{Purpose and Conceptual Model}

The chronological view reorganises the same patient data into a time-oriented
representation rendered using D3.js. Its purpose is to support
\textbf{temporal reasoning} by allowing clinicians to read the patient journey
as a sequential narrative. Unlike the categorical view, which emphasises
relationships, the chronological view emphasises event order, time intervals
between clinical decisions, and the progression of care across time
\cite{patientSafetyDashboards2021}.

\subsubsection{Temporal Layout and Event Stacking}

Events are distributed along a horizontal timeline scaled by a configurable
\texttt{DATE\_SCALE} constant, ensuring even temporal spacing regardless of
event density. Each unique date is marked with a vertical tick and label
rendered by the \texttt{drawDateMarkers} function. When multiple events occur
on the same date within the same lane, they are stacked vertically using an
alternating offset algorithm that places successive same-date nodes above and
below the lane centreline, preventing overlap while preserving temporal
accuracy.

The entire canvas supports pan and zoom via D3's \texttt{zoom} behaviour, with
a configurable scale range of 0.05\texttimes{} to 3\texttimes{}. An automatic
fit-to-view transform is computed and applied immediately after each render,
ensuring the full timeline is visible on first load regardless of data density.

\subsubsection{Branching Mechanism for Clinical Reasoning}

A key feature of the chronological view is its branching mechanism. The main
timeline represents the primary clinical pathway. When diagnostic uncertainty
arises or alternative treatment strategies must be explored, clinicians can
create independent sub-branches by activating the \textbf{branch creation
button} (a blue code-branch icon in the bottom-right corner) and clicking any
main-timeline node. This action opens the node creation form with the category
preset to ``Diagnosis'', and the resulting node is flagged with
\texttt{isDiagnosis: true} and \texttt{isManualBranch: true}.

Sub-branches are rendered as distinct horizontal tracks below the main
timeline, connected to their origin on the main line via smooth cubic B\'{e}zier
divergence paths drawn by the \texttt{generateLinkPath} function. Each branch
maintains its own horizontal baseline drawn at a fixed vertical offset
determined by \texttt{BRANCH\_VERTICAL\_GAP}, ensuring consistent visual
separation between parallel clinical reasoning paths.

Branching from an existing branch is explicitly prohibited; a contextual
toast message is displayed if this is attempted, guiding the user to branch
only from main-timeline nodes. This constraint reflects the clinical model
that sub-branches represent direct hypotheses against the main care pathway.

\subsubsection{Branch State Management}

Every branch carries a \textbf{branch state} that governs its visual
presentation and edit permissions:

\begin{itemize}
    \item \textbf{In Progress} (blue): The branch is active. Nodes may be
          added, edited, and deleted freely.
    \item \textbf{Discontinued} (red): The branch has been ruled out. A
          prominent ``DISCONTINUED'' wall marker and pulsing wall animation are
          rendered at the branch terminus. All add, edit, and delete operations
          within the branch are blocked with an explanatory message.
          Figure~\ref{fig:chrono_discontinued} shows a zoomed view of a
          discontinued branch.
    \item \textbf{Completed} (green): The branch has been validated and merged
          back into the main timeline. A green curved merge arc is drawn from
          the branch's last node to the nearest main-timeline node, and a
          ``MERGED'' label is rendered above the arc. If the branch's last event
          post-dates all main-timeline events, the system automatically creates
          a \textit{Linker} node on the main timeline at that date to serve as
          the merge target, ensuring geometric accuracy of the arc.
          Figure~\ref{fig:chrono_completed} shows a zoomed view of a completed
          and merged branch.
\end{itemize}

Branch state is changed by clicking the branch line itself to open a
state-selection menu. The main timeline also carries a state that can be
set to \textbf{Finish Case}, which renders a ``CASE CLOSED'' flag at the
timeline terminus, displays a ``Case Finished'' banner in the header, and
blocks all modifications to the entire graph until the case is reopened.

\subsubsection{High-Priority Visualisation}

High-priority events in the chronological view are highlighted using a red
``HIGH PRIORITY'' label rendered beneath the node's date stamp. This visual
hierarchy ensures that urgent clinical issues remain immediately noticeable
within the temporal flow regardless of zoom level.

\subsubsection{Stateful Mode Switching}

A toggle control in the header allows instant switching between categorical
and chronological views. This interaction is fully stateful: all filter
selections, expansion state, and data mutations carry over seamlessly between
modes. No page reload is required, and the \texttt{refreshGraph} function
pointer is reassigned to the appropriate renderer on each mode switch, ensuring
that subsequent filter changes or node operations automatically re-render in
the correct mode.

\subsection{Complementary Roles of the Two Views}
% -----------------------------------------------------------

The categorical and chronological views address fundamentally different
cognitive tasks. The categorical view focuses on \textbf{structural
understanding}, enabling clinicians to reason about relationships,
dependencies, and complete clinical paths. The chronological view focuses on
\textbf{temporal understanding}, enabling clinicians to interpret the sequence
and timing of events and to visualise parallel reasoning paths.

Providing both views allows clinicians to:
\begin{itemize}
    \item Understand how events are connected (categorical).
    \item Understand when events occurred and how the case evolved (chronological).
    \item Reduce cognitive load by selecting the most appropriate representation
          for the current analytical task.
\end{itemize}

This dual-view approach follows established guidelines for multiple coordinated
visualisations, which have been shown to improve usability and analytical
effectiveness in complex information systems \cite{hospitalDashboards2022}.

\subsection{AI-Assisted Clinical Chat}
% -----------------------------------------------------------

The \texttt{ChatSection} component provides an integrated AI chat interface
accessible from within the MedGraph view, supporting real-time clinical
reasoning alongside patient journey data. The component is designed for
sustained, multi-turn clinical dialogue and incorporates a range of usability
features tailored to medical workflows.

\subsubsection{Conversation and Session Management}

The chat interface maintains a list of named conversation sessions. A ``New
Chat'' action saves the current session's messages and initialises a blank
session. Switching between sessions restores the full message history for the
selected session. Sessions are auto-titled from the first user message
(truncated to 27 characters for display), and titles can be manually edited
inline via a double-click interaction on the session list item.

A search field filters the session list in real time, matching sessions by
title prefix.

\subsubsection{Message Composition and Input Controls}

The message composer features a self-expanding textarea that grows vertically
up to a maximum of 180 pixels as the user types, implemented via the
\texttt{autoResize} event handler. File attachments (images and PDFs) can be
added via a file picker; attached files are base64-encoded and displayed as
inline previews in the outgoing message bubble, with individual removal
controls. A voice input button activates the Web Speech API
(\texttt{webkitSpeechRecognition}) for continuous speech-to-text input with
real-time interim transcript display.

\subsubsection{Response Mode Selection}

Four response modes, Concise, Detailed, Bullet Points, and Differential,
allow the clinician to specify the desired output format for AI responses,
adapting the interface to different clinical contexts such as rapid triage
versus comprehensive case review.

\subsubsection{Message-Level Interactions}

Each AI response bubble exposes a set of interaction controls:
\begin{itemize}
    \item \textbf{Like / Dislike}: Binary feedback toggles allowing the
          clinician to rate response quality.
    \item \textbf{Copy}: Copies the full response text to the clipboard.
    \item \textbf{Retry}: Replaces the AI response in-place with a new
          generation, preserving conversation position.
    \item \textbf{Fork}: Opens a new browser tab pre-loaded with a snapshot
          of the conversation up to and including the selected response,
          encoded in URL parameters, allowing independent exploration of
          alternative follow-up threads from any prior point.
    \item \textbf{Delete}: Removes the AI response and its corresponding user
          message from the session.
    \item \textbf{Citations}: Opens an inline citations panel listing the
          reference sources associated with the AI response.
\end{itemize}

A confidence score is displayed with each AI response, giving the clinician a
visible signal of response certainty.

\subsubsection{Maximised View and Branch Tabs}

The chat panel supports a maximised mode that expands the component to fill
the available viewport, providing a focused environment for extended clinical
dialogue. Sessions opened via the Fork action automatically launch in
maximised mode and display a visual divider message indicating the branch
origin session and message index, preserving chain-of-custody of the
conversation thread.

\subsection{Domain Models and State Services}
\label{subsec:state-management}
% -----------------------------------------------------------

Shared domain concepts are defined in the \texttt{models} directory. The
\texttt{patient.model.ts} file formalises the patient entity, covering
identifiers, metadata, episodes, encounters, and associated medical events,
and provides all FHIR-to-DTO transformation functions as pure, stateless
utilities.

Application-wide state is managed via injectable Angular services:

\begin{itemize}
    \item \texttt{PatientApiService}: Responsible for all patient-related API
          communication, including FHIR resource retrieval, graph node
          operations, and binary resource resolution for lab PDF viewing.
    \item \texttt{SelectedPatientService}: Maintains the currently active
          patient context as a BehaviourSubject, enabling any component in the
          tree to subscribe to patient selection events without tight coupling.
    \item \texttt{HandshakeService}: Encapsulates the OTP verification and
          grant status polling API calls.
    \item \texttt{AppointmentService}: Manages all schedule and slot CRUD
          operations.
    \item \texttt{AuthService}: Wraps the Keycloak authentication status check
          used by both the auth guard and the doctor profile loader.
\end{itemize}

By centralising patient selection and API communication in services, multiple
components can synchronise reactively without direct dependencies, reducing
tight coupling and improving testability \cite{angularDocs}.

\subsection{Error Handling and Resilience}
% -----------------------------------------------------------

The frontend implements a layered error-handling strategy. At the route level,
a dedicated \texttt{GatewayErrorComponent} handles arbitrary HTTP error codes
received as route parameters, rendering a contextual error page without
exposing raw stack traces.

At the component level, all API subscriptions include \texttt{error} handlers
that set typed error state variables rendered as user-facing messages. The
MedGraph's optimistic update pattern provides full rollback for all three node
operation types: added nodes with temporary IDs are spliced from the data array
on failure; edited nodes are restored from a \texttt{pendingEdits} snapshot
map; deleted node trees are fully restored from a \texttt{pendingDeletes}
collection. This ensures the visual state of the graph remains consistent with
the backend at all times, even under intermittent network conditions.

\subsection{Architectural Rationale}
\label{subsec:architecture-rationale}
% -----------------------------------------------------------

The architectural decisions underlying the CFI-Care frontend were driven by
four primary constraints:

\begin{enumerate}
    \item \textbf{Visualisation Complexity}: Medical journey graphs require
          custom SVG layouts, zoom behaviours, and stateful interaction patterns
          that are not supported by standard Angular UI libraries.
    \item \textbf{Performance}: D3.js performs intensive DOM mutations that
          would trigger excessive Angular change-detection cycles if executed
          within the component tree.
    \item \textbf{Maintainability}: Clinical logic, routing logic, FHIR
          transformation logic, and graph rendering logic must evolve
          independently without cross-cutting refactoring.
    \item \textbf{Data Integrity}: Optimistic updates require a principled
          rollback strategy at every operation type to prevent UI state from
          diverging from persisted backend state.
\end{enumerate}

The iframe isolation boundary directly addresses constraints 1 and 2. The
service layer and domain model separation address constraint 3. The
\texttt{pendingEdits} and \texttt{pendingDeletes} maps address constraint 4.
Together, these decisions produce a system that is both clinically capable
and structurally sound for continued development \cite{componentFrontEnd2021}.

\subsection{Graph Logic Test Suite}
\label{subsec:test-suite}
% -----------------------------------------------------------

To validate the correctness and robustness of the graph engine's JavaScript
logic, a dedicated browser-based test suite was developed for the CFI-Care
patient journey graph. The suite targets the pure JavaScript functions that
govern the graph's data model and rendering pipeline, testing them directly
in isolation from the graph's visual layer. This approach ensures that the
core clinical logic, including node hierarchy management, branch state
transitions, chronological sorting, filter evaluation, and recursive tree
operations, is verified independently and reproducibly.

\subsubsection{Test Architecture}

Rather than loading the full graph interface during testing, the suite
reconstructs a controlled mock environment in JavaScript that mirrors the
graph's internal data structures and pure functions exactly. This allows every
test to run deterministically in the browser without network dependencies,
iframe loading times, or DOM rendering variability. The mock environment
reproduces the twelve-node baseline dataset used throughout the system,
covering all nine clinical categories, all three priority levels, all three
normality values, and a representative branch with in-progress state.

\subsubsection{Test Suites and Coverage}

The suite is organised into five suites totalling 62 test cases, all of which
pass with zero failures and zero warnings, completing in 22ms total. The five
suites and their scope are as follows.

\textbf{Functional Tests (21 cases)} validate the core data model and node
operations. Tests verify that the dataset maintains a single root node with a
\texttt{null} father, that all non-root nodes reference existing parents, that
no circular parent references exist, and that all required fields are present
and valid. Node operations are tested end-to-end: adding a node confirms the
correct parent-child relationship is established; deleting a node via
\texttt{deleteRecursive} confirms the target is removed and all descendants are
removed recursively, while siblings are preserved. Branch logic tests confirm
that \texttt{isNodeInRejectedBranch} and \texttt{isNodeInCompletedBranch}
correctly traverse the ancestor chain for both discontinued and completed
branch states, and that linker node detection operates on both the
\texttt{category} field and the \texttt{\_linkedBranchId} flag.

\textbf{Chronological View Tests (15 cases)} validate the
\texttt{getChronologicalData} function that drives the D3.js timeline. Tests
confirm that the full dataset passes through with default filters, that output
nodes are sorted in non-decreasing date order, that main-timeline nodes receive
\texttt{laneId = 0} and branch nodes receive \texttt{laneId > 0}, and that all
members of a branch share the correct \texttt{branchStartId}. Filter
correctness is verified across all three dimensions (category, priority,
normality) individually, as well as date-range filtering and
\texttt{isDiagnosis} suppression. Mutation tests confirm that newly added nodes
appear in output and that deleted nodes are absent. A multi-branch test
confirms that two independent diagnosis branches receive distinct lane
identifiers.

\textbf{Categorical View Tests (7 cases)} validate tree structure invariants
required by the Treeviz rendering layer. Tests confirm that exactly one root
node exists, that node depth is computed correctly (node~10 sits at depth~3),
that sibling detection correctly identifies all five children of the root, that
the \texttt{MAX\_EXPANDED = 2} concurrency limit evicts the oldest expanded
branch when a third is activated, that linker nodes are excluded from the
categorical view, that a virtual root is correctly inserted when multiple roots
are present, and that the recursive collapse function removes all descendants
from the visible set.

\textbf{Boundary and Validation Tests (12 cases)} probe edge conditions and
guard logic. Tests cover single-node and empty datasets, 500-character node
titles, epoch-dated and far-future nodes (sorting to the correct ends of the
timeline), deletion of the root node (removing all 12 nodes), case-sensitivity
rejection of a malformed category value, leaf-node collection, and both
guard-logic scenarios in which attempting to add a child to a node inside a
discontinued or completed branch is correctly blocked.

\textbf{Performance Tests (7 cases)} set explicit time budgets for all
computationally intensive operations and warn if any budget is exceeded.
\texttt{getChronologicalData} must complete in under 5ms averaged over 100
iterations on the 12-node dataset, and under 30ms on a synthetically generated
500-node dataset. \texttt{collectNodesRecursive} must average under 2ms over
200 iterations. \texttt{isNodeInRejectedBranch} must average under 1ms over
500 iterations on a 50-node deep chain. \texttt{deleteRecursive} on the full
12-node tree must average under 1ms over 100 iterations. The triple-filter
pipeline (category, priority, normality) on 500 nodes must average under 3ms
over 50 iterations. A memory integrity test confirms that all read-only
operations leave the original data array length unchanged across 50 iterations,
detecting any inadvertent side effects.

\subsection{Summary}
% -----------------------------------------------------------

The CFI-Care frontend successfully transforms fragmented clinical data into a
coherent, interactive medical information system. Through a carefully layered
Angular architecture, a semantically rich visualisation engine combining
Treeviz and D3.js, an OTP-based patient access workflow, a full AI-assisted
clinical chat interface, and a practitioner scheduling system, the frontend
addresses the complete spectrum of clinical interaction requirements. The
dual-view Patient Journey Dashboard, with its categorical tree and
chronological timeline, provides clinicians with both structural and temporal
analytical perspectives from a single, seamlessly navigable interface. The
built-in tutorial system, optimistic update strategy, dark mode support, and
branch state management together reflect a commitment to usability, resilience,
and clinical safety that underpins every design decision made during this phase
of development.
